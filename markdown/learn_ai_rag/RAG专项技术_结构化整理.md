# RAG 专项技术（结构化整理版）

> 本文按 RAG 的数据流重组：数据入库 → 召回与排序 → 上下文与生成 → 高级架构 → 运营评估。固定规模、阈值、压缩率和产品选型均属于经验示例，不应替代针对数据集、模型和硬件的压测。

## 1. 全景：RAG 的基本链路

RAG（Retrieval-Augmented Generation，检索增强生成）的基本流水线是：

```text
数据源 → 解析 / 清洗 → Chunking → Embedding → 向量库 / 索引
用户问题 →（Query Rewrite）→ Embedding → 召回（向量 / BM25）→ 融合 → Rerank
       → 上下文组装与预算管理 → RAG Prompt → LLM 回答（带引用 / 拒答）
```

- 传统 RAG 是相对固定的线性流程：用户提问 → 检索 → 组装 → 生成回答。
- 当第一次检索不理想时，传统流水线往往只能“将错就错”；Agentic RAG 则可让 Agent 决定是否检索、如何拆题、是否继续检索和调用什么工具。

## 2. 入库与知识表示

### 2.1 向量化（Embedding）

#### 本质

向量化是将**文本或媒体**转化为高维空间中的一组数字（向量），从而用于表示和比较语义。

#### 作用

1. **将文本转化为“语义坐标”**
    - 语义相近，空间距离通常也更近：在向量空间中，“猫”和“狗”的距离会比“猫”和“汽车”的距离更近。
    - 能在一定程度上处理同义表达和多义词：例如识别“电脑”与“计算机”的相近含义，或结合上下文区分“苹果”是水果还是手机品牌。
2. **RAG 中的高效语义检索基础**
    - 将用户提问（Query）和知识库文档块（Chunks）映射到同一向量空间。
    - 用余弦相似度等度量，在百万级文档中筛选 Top-K 相关片段，供大模型作为参考资料；毫秒级是常见的工程目标。
3. **多模态桥梁**
    - 适用的多模态嵌入模型可以把文字、图片、音频，甚至视频映射到共享空间。
    - 例如输入“奔跑的马”检索马的图片，实现以文搜图。

#### Embedding 模型：关注点

- 通常由模型提供方提供，输出维度由模型决定；其职责是将数据源和查询转为向量。
- 选择时关注：
    - **维度**：输出向量的数字长度。
    - **最大输入 Token 限制**：单次送入模型进行向量化的最大文本长度。
    - **检索指标**：
        - `NDCG@10` / `NDCG@5`：衡量前 5 或前 10 个结果的排序质量，越相关的结果越靠前，分值越高。
        - `Hit Rate`（命中率）：标准答案是否存在于 Top-K 结果中。
    - **语言与领域支持**：单语（如仅中/英）或多语（Multilingual），以及对目标领域的支持。
    - **调用成本**：通常按每百万 Token 计费；例如 OpenAI `text-embedding-3-small` 约 `$0.02 / 1M tokens`。

#### 维度（Dimension）

维度代表向量空间中独立坐标轴的数量。若将向量视为一个人的“画像”，维度相当于描述它的特征标签数量（如身高、体重、职业、爱好）。

- **约束**：数据用 Embedding 模型输出的维度，必须与向量数据库 / collection 定义的维度一致。
- **权衡**：维度影响表达能力、存储、索引构建和相似度计算开销。
    - **高维（如 1536、3072）**：有更多空间捕捉细微语义、语气、上下文背景和专业术语。
    - **低维（如 256、384）**：特征空间较小，通常只保留较粗粒度的语义，可能丢失细节。
    - 维度增加会增加内存 / 显存占用、索引构建时间和相似度计算成本；具体增长方式取决于索引和硬件，需实测。
- 场景划分：
    - **轻量级（384–768）**：速度快、省内存，复杂长文本能力相对较弱；适用于手机端本地部署、Q&A 问答对匹配、预算和内存极受限的场景。
    - **标准型（1024–1536）**：在语义准确度和性能间平衡；适用于企业知识库、文档检索、客服机器人等通用 RAG。
    - **重量级（3072 及以上）**：语义捕捉更精细，内存和计算消耗更高；可用于法律条文对比、医疗病历检索、深度学术论文分析等。

### 2.2 Chunk（分块）与 Chunking

#### 为什么要分块

- **语义聚焦，提高向量检索精准度**：例如将大文档拆为约 200 字的小块，使每个 Chunk 更聚焦于一个话题。
- **突破模型上下文窗口限制**：只把与问题相关、合计数千字以内的 3–5 个 Chunk 提供给大模型。
- **节省成本、提升响应速度**：输入 Token 数通常直接影响大模型计费、推理延迟和 TTFT。
- **减少幻觉风险**：极长文本中间的信息可能被模型忽略；先检索相关内容再提供，可降低该风险。
- **一句话**：把大象（海量长文本）切成小肉块，让向量检索“好找”，让大模型“好消化”。

#### 基本概念

- **Chunk**：以某种策略把较大数据源切成多个块，然后向量化。切分混乱或切断连贯上下文会降低检索效果。
- **Chunk Size**：每个块的目标长度；应以模型 Token 作为主要度量，而不是只看字符数。
- **Chunk Overlap**：相邻块的重叠内容，用于避免信息刚好在边界断裂。

#### 常见切分策略

1. **定长切分**：实现简单，但语义和结构破坏较多，通常效果较差。
2. **递归分块（Recursive Chunking）**：常用且效果较好的通用策略，核心是“由大化小、层层递进”。
    - 使用有优先级的分隔符（如段落、换行、句号、空格），在长度限制内尽量保持语义完整。
    - 示例分隔符顺序：`\n\n` → `\n` → 空格 → 空字符。
    - 切分逻辑：
        1. 先用最高优先级分隔符（如 `\n\n`）切整篇文章。
        2. 长度低于目标（如 500 Token）的块直接保留。
        3. 超过 500 Token 的块降级使用下一个分隔符（如 `\n`）继续切。
        4. 直到所有块符合长度限制。
3. **语义化分块**：借助模型识别语义边界。
4. **结构化分块**：按文档结构切分；例如 Markdown 通常按标题层级（`#`、`##`）切分更合理。

#### 分块常见问题与对策

| 问题         | 表现                                                                             | 对策                                                                                                                    |
|------------|--------------------------------------------------------------------------------|-----------------------------------------------------------------------------------------------------------------------|
| 语义断裂、上下文丢失 | 一个完整句子或逻辑段落被生硬切为两半；检索到后半句时缺少背景                                                 | 优先使用递归字符切分（段落 `\n\n`、句子 `。！？`，超长再硬切）；设置 10%–20% Overlap（例：Chunk 512、重叠 50–100 字符）；检索阶段采用邻居扩展。                         |
| 结构破坏       | 表格表头在 Chunk A、数据行在 Chunk B；代码块或列表被切碎                                           | 布局感知解析：用 Unstructured、Marker、PyMuPDF 等先把 PDF / Markdown 的表格提取为独立 HTML 或 Markdown，并强制作为整体 Chunk；按 Markdown 标题级别结构感知切分。 |
| 指代不明、主语缺失  | 前文提到“华为 Mate 60”，后文仅说“该手机”“它”“这款产品”；切片后失去主语                                    | 将文档标题、章节名、关键词作为 Metadata 拼到每块开头或写入元数据；也可用轻量 LLM 补全省略主语或添加 3 个核心关键词，再用重写文本生成向量。                                        |
| 块大小难平衡     | 过大（如 2000 字符）造成语义稀释、检索不准、浪费 Token；过小（如 100 字符）则信息不足                            | 采用父子块架构：用小子块检索，向 LLM 提供命中的父块，以平衡精度与上下文。                                                                               |
| 特殊文本处理失败   | 英文单词可能被截断（`Transformer` → `Trans` / `former`）；版本号 `v3.14` 的点被误作句尾；代码和公式闭合语法被破坏 | 按 Token 而非纯字符数切分；使用正则保护数字、版本号、英文缩写（例如：`optimized_regex = r'。                                                        |(?<!\d)\.(?!\d)(?<!e\.g)(?<!i\.e)'`）；代码、JSON、LaTeX `$$ ... $$` 等使用 AST、Markdown 专用切分器等语法感知方案。 |

### 2.3 Metadata（元数据）

#### 本质与作用

Metadata 是与向量数据绑定存储的结构化键值对（Key-Value Pairs）。它可在向量检索时进一步过滤匹配结果，支持权限隔离、引用溯源、时效性排序，以及父子块检索等高级策略。

#### 常用分类

| 分类      | 字段示例                                                                 | 用途                                                                           |
|---------|----------------------------------------------------------------------|------------------------------------------------------------------------------|
| 文档溯源    | `source_id` / `doc_id`、`file_name` / `file_path`、`page_number`、`url` | 记录原始大文档唯一 ID、文件名 / 路径（如 `s3://bucket/docs/policy.pdf`）、PDF / Word 页码、网页原始链接。 |
| 内容结构    | `chunk_id`、`parent_id`、`heading` / `section`                         | 记录当前分块唯一 ID、父块 ID，以及如“第三章 薪酬福利”的章节标题。                                        |
| 业务管理与权限 | `category` / `tag`、`user_id` / `tenant_id`、`access_level` / `role`   | 记录 HR、财务、技术文档等分类；多租户隔离；`admin` / `public` / `internal` 等权限，防止越权。             |
| 时效性     | `created_at` / `updated_at`、`version`                                | 标识创建或更新时间，以及 `v1.0`、`v2026_Q1` 等版本。                                          |

### 2.4 增量索引

#### 作用

数据源变化时，仅对新增、删除、修改的文档和 Chunk 处理与建索引。

#### 状态追踪机制

- **哈希校验法（常用）**：可对原始文档和 Chunk 用 MD5 跟踪。
- **时间戳 / 版本号轮询**：依赖源系统 `updated_at` 或版本字段；每次同步只取 `updated_at > Last_Sync_Time` 的数据。
- **CDC（Change Data Capture，变更数据捕获）**：若数据源是 MySQL、PostgreSQL 等关系数据库，可监听数据库 Binlog / WAL 等变更日志。

## 3. 检索、召回与排序

### 3.1 Vector DB（向量数据库）

可按数据规模初步选择候选；实际还应评估过滤能力、延迟 / QPS、数据更新、运维模式、可用区和总拥有成本。

| 参考规模区间 | 候选                                       | 特点                                                                                                                |
|--------|--------------------------------------------|---------------------------------------------------------------------------------------------------------------------|
| 十万内    | Chroma、FAISS                               | 轻量选择。                                                                                                               |
| 百万级以内  | Redis                                      | 受限于内存成本。                                                                                                            |
| 千万级至亿级 | Qdrant、Weaviate、pgvector                   | Qdrant：Rust 编写、单机性能高且支持分布式；Weaviate：Go 编写、图索引优化、支持云端与分布式；pgvector：PostgreSQL 插件、生态佳，随主库性能扩展，通常适合千万级以下。            |
| 亿级以上   | Milvus、Elasticsearch / OpenSearch、Pinecone | Milvus：存算分离，面向百亿级海量向量的专业分布式数据库；Elasticsearch / OpenSearch：成熟分布式引擎，适合文本与向量混合检索；Pinecone：云原生全托管 SaaS，可自动扩容、免运维承载海量数据。 |

### 3.2 快速检索算法：ANN

#### ANN（Approximate Nearest Neighbor，近似最近邻）

ANN 不是单一算法，而是一类以少量精度换取检索速度的技术分类。

| 算法              | 原理                 | 优点                    | 局限                          | 适用判断           |
|-----------------|--------------------|-----------------------|-----------------------------|------------------|
| HNSW（分层可导航小世界图） | 基于图（Graph）的 ANN 索引 | 速度快、召回率高，是 RAG 常见核心索引 | 维护图结构会消耗较多 RAM              | 预算充足且追求高召回的 RAG。 |
| IVF（倒排文件索引）     | 基于聚类 / 分组          | 不需复杂图结构，内存占用相对低       | 边界向量可能漏召回；准确率和极端性能通常不如 HNSW | 数据量极大、内存预算有限。    |

### 3.3 向量压缩与量化

#### 目的

降低大规模向量在磁盘或内存中的占用。

#### 算法与经验参数

| 方法          | 压缩率 / 特征   | 适用场景或说明                                    |
|-------------|--------------|----------------------------------------------|
| 无压缩（FP32）   | 内存消耗最高、精度最高  | 原始精度基准。                                      |
| 半精度（FP16）   | 约 2× 压缩      | 硬件支持 GPU 加速且需兼顾高精度。                          |
| SQ（标量量化）    | 约 4× 压缩      | 适合绝大多数通用生产 RAG，准确率损失通常较小（如 `<1%–2%`）。 |
| BQ（二进制量化）   | 约 32× 压缩     | 海量数据第一轮高速粗筛，需配合重排。                           |
| PQ（乘积量化）    | 约 16×–64× 压缩 | 亿级以上、内存极受限；准确率损失示例为 5%–15%。                 |
| OPQ（优化乘积量化） | 约 16×–64× 压缩 | 维度关联性强、追求高召回的超大规模库；准确率损失通常小于 PQ。              |
| RVQ（残差量化）   | 约 16×–64× 压缩 | 深度学习高级索引、多级向量检索方案。                           |

> `PQ` 的“子主题”尚待展开。

#### 工业级做法：两阶段检索 / Rescoring

为兼顾低成本和精度，可组合量化和精排：

1. 先用 SQ8 或 BQ 等压缩向量在内存中快速粗筛 Top-100。
2. 将原始 FP32 向量保存于硬盘等较低成本介质。
3. 用原始向量对这 100 个候选做精准重排（精筛）。

### 3.4 Top-K Retrieval

#### 定义与过程

Top-K 检索是从所有候选数据中找出与 Query 最相关的前 K 个结果：

1. **向量化提问**：使用 Embedding 模型将 Query 转为向量。
2. **计算相似度**：计算 Query 向量与文档块向量的距离 / 相似度，如余弦相似度。
3. **排序和截取**：按相似度排序，返回得分最高的 K 个片段。

#### K 值的权衡

| K 值          | 优点                      | 风险                                                 |
|--------------|-------------------------|----------------------------------------------------|
| 小（如 2 或 3）   | 上下文精简、生成更快、API 费用低、噪声少  | 复杂问题可能漏掉关键资料，召回不足。                                 |
| 大（如 15 或 20） | 更可能覆盖全部相关资料，Hit Rate 更高 | Token、延迟和成本上升；无关信息可能干扰模型，并加剧 “Lost in the Middle”。 |

### 3.5 Recall（召回率）

#### 定义

召回率衡量“找得全不全”：

```text
Recall = 检索出的相关 doc 数量 / 实际存在的全部相关 doc 数量
```

#### 提升方式

- 增大 Top-K：如从 Top-5 增至 Top-20。
- 使用混合检索：语义向量检索负责语义相关，BM25 负责精确产品型号、人名等字面关键词，降低语义偏差导致的漏召回。
- 优化 Chunking：使用 Recursive Chunking 和合理 Overlap，避免核心答案被切成两半、向量特征变弱。

### 3.6 Keyword Search / BM25

#### 作用与意义

BM25（Best Matching 25）是经典的关键词检索打分算法，基于词项匹配和统计特征进行排序，可视为基于字面匹配的传统检索技术。它可补足向量检索对冷门产品型号、长代码块、特定专有名词容易泛化失效的问题；Lucene / Elasticsearch 等搜索系统广泛使用 BM25 类相关性模型。

#### 工业级做法：双路并发

```text
向量检索：语义相关 Top-50
BM25 检索：字面精确 Top-50
              ↓ 合并
          Reranker（重排）
              ↓
           最终 Top-5
```

### 3.7 混合检索融合算法

混合检索将向量检索与 BM25 的结果集合并为新的候选集（如 Top-50）。

| 方法                                 | 特点              | 适用场景             |
|------------------------------------|-------------------|--------------------|
| RRF（Reciprocal Rank Fusion，倒数排名融合） | 复杂度低、性能高、准确率稳定    | 通用 RAG 项目。         |
| 线性加权（MinMax）                       | 复杂度低、性能高，准确率受权重影响 | 两路分数分布非常稳定的简单场景。   |
| Reranker（重排模型）                     | 需单独模型，复杂度较高，准确率高  | 企业级、生产级 RAG 的最终排序。 |

### 3.8 Rerank（重排）

#### 定义

将首次向量检索的 Top-K 结果和问题一并交给专门重排模型，进行二次相关性排序，再截取最终 Top-5（示例）。

#### 解决的痛点

1. **减轻长上下文中的信息迷失**：粗筛 Top-50 直接交给 LLM 会带入太多内容；重排将高质量答案前置，提高回答准确率。
2. **过滤不相关候选**：可设置绝对置信度门槛。向量相似度（如 `0.85`）跨模型通常不可横向比较；若重排后最高分很低（如 `0.05`），可丢弃全部上下文并回答“知识库中查无此项”，降低幻觉风险。

#### 模型选择

- 可选用低成本模型配合恰当提示词。
- 也可使用专用模型，如 `bge-reranker-v2-m3`。这类模型通常以 Query-Document 为输入，通过专用接口直接返回相关性分数，而不是依赖通用提示词。

### 3.9 Query Rewrite（查询改写）

#### 定义

在 Query 进入向量库前，对原问题加工、润色或拆解，使检索系统更准确理解真实意图。

#### 触发背景

1. **多轮对话指代不明**：第一句“周杰伦是谁”，第二句“它有多少专辑”；第二句直接向量检索会缺少指代对象。
2. **问题太短或口语化**：如“高血压吃啥药？”；企业医疗库内可能有大量相关疾病与用药信息，直接检索易混乱。
3. **一个问题包含多个子问题**：如“对比一下 iPhone 16 和 15 的续航，顺便把价格也发我”，同时包含“16 续航、15 续航、16 价格、15
   价格”四个检索维度。

#### 实现策略

实际工程通常用成本较低、响应较快的小型 LLM 加提示词实现：

1. **核心提炼与去噪**：去掉语气词和冗余，补全对话代词。
2. **扩展 / 生成多个同义问法**：从不同角度生成 3–5 个语义相同、措辞不同的问题。
3. **假设性文档生成**：先生成一个可能不准确的假设答案，再将其向量化用于检索。

### 3.10 邻居扩展（Neighbor Expansion）

#### 目标与核心方案

邻居扩展解决“检索命中的 Chunk 不含完整上下文，导致交给 LLM 的语料不完整”的问题：

```text
向量检索定位命中 Chunk + 基于物理索引还原前后邻居
```

#### 触发条件

可根据以下信号触发，而不是对所有结果无差别扩展。

1. **基于召回文本的语义连贯性**
    - 句式：问题询问步骤、前提、原因、对比时通常需要连续上下文。
        - `containsAny(query, "如何", "步骤", "前提", "为什么", "原因", "区别", "优缺点")`
    - 开头指代 / 连接词：`然后、因此、此外、但是、该、此、上述、它、this、however` 等开头的块，上文可能定义了指代对象。
        - `startsWithAny(text, "然后", "因此", "此外", "但是", "该", "此", "上述", "它", "this", "however")`
    - 结尾未完成：块以 `：`、`,`、`，`、`(`、`（`、`{`、`` ``` `` 等结尾时，下文可能包含结论。
        - `endsWithAny(text, "：", ",", "，", "(", "（", "{", "```")`
    - 块过短：常是标题、列表项或边界残片。
        - `utf8.RuneCountInString(text) < 120`
2. **基于 Query 类型**
    - 高触发意图：流程类、因果推理类、长故事线，例如“XX 事件的前因后果是什么？”“这个操作的具体步骤是什么？”。
    - 低触发意图：事实型、短实体检索，例如“周杰伦的生日是哪天？”“特定产品的型号是什么？”，闭环语义可能已足够。
3. **基于检索分数边界**
    - 核心 Chunk 的向量相似度极高、检索方向很明确，但长度较短时，可触发扩展。

## 4. 上下文组装与回答生成

### 4.1 父子文档检索（Parent-Child Retrieval）

#### 作用与背景

父子文档检索用于调和“检索精度”与“LLM 上下文完整度”的矛盾：

- 切小块：模型更容易命中，但上下文不足。
- 切大块：语义被稀释，检索命中率下降。

#### 实现：大包小、用小捞大

1. **数据准备阶段**
    - 定义父文档（Parent Docs）：原始长文按章节等方式切为较大段落，例如每块 1000–2000 字。
    - 定义子文档（Child Chunks）：在父文档内进一步切为细粒度片段，例如每块 150–200 字。
    - 建立映射：
        - 向量数据库只对**子文档**进行 Embedding；子文档 Metadata 记录 `parent_id`。
        - 关系库 / 内存键值库（Docstore）以 `parent_id` 存储完整**父文档**内容，降低向量库显存和索引资源压力。
2. **在线检索阶段**
    - 用户提问后，在向量库检索 3–5 个相关子文档。
    - 不直接把零碎子文档交给 LLM，而是读取其 `parent_id`。
    - 从 Docstore 取出对应的完整父文档，组装进 Prompt。

#### 优势

子文档保障检索颗粒度和召回，父文档提供逻辑连贯的生成上下文，从而兼顾检索准确率与回答质量。

### 4.2 Context Window 管理

#### 意义

上下文窗口管理直接影响 Token 成本、响应延迟和答案质量。

#### 方法

1. **动态 Token 预算分配**

   ```text
   可用检索上下文 = 最大窗口 - 系统提示词 - 历史聊天记录 - 预期输出空间
   ```

   不能仅按字数估算，应在代码端用与模型对齐的 Tokenizer（如 OpenAI 的 `tiktoken`）实时计算。

2. **检索内容的动态漏斗与过滤**
    - Reranker 分数截断：例如仅保留重排后 `> 0.5` 的内容。
    - 信息密度压缩：如 LLMLingua 算法，在入模前用轻量模型识别并移除助词、冗余格式、重复表述等低信息内容；在不损失核心语义的前提下可压缩 2×–5×。
3. **历史聊天记录剪枝 / 压缩**
    - 滑动窗口：保留最近 N 轮对话。
    - 总结摘要：用成本较低的模型定期总结久远历史；窗口仅保留 `[长期历史摘要] + [最近 2 轮详细对话] + [当前 RAG 资料]`。
4. **缓解“迷失在中间”的排列策略**
    - 模型通常对上下文开头（Head）和结尾（Tail）更敏感，中间（Middle）信息更易被忽略。
    - 将 Reranker 得分最高、最相关的文档放在开头和结尾，相关性较低的内容放中间。

### 4.3 RAG Prompt

#### 定义与目标

RAG Prompt 是发送给 LLM 的最终核心指令模板。目标是要求 LLM 基于检索资料回答；没有资料时明确说明“知识库没有结果”。

#### 生产实践中的四个板块

1. **角色与人设**：例如“你是一位严谨的企业知识库 AI 助手”，用于约束语气和专业度。
2. **边界与纪律**：要求严格根据参考资料回答，资料不足时拒答，降低幻觉。
3. **动态插值槽**：明确放入 `【参考资料】{CONTEXT}` 和 `【用户提问】{QUERY}`。
4. **输出格式与引用**：要求答案句末标注文档名、页码等 Metadata 来源，例如 `[文档名_页码]`。

#### 示例模板

```text
# 角色
你是一位专业、严谨的企业内部知识库问答助手。

# 核心指令（考场纪律）
1. 请仔细阅读下方提供的【参考资料】，并仅根据这些资料回答用户的【提问】。
2. 你的回答必须完全忠实于参考资料，不得包含任何资料中未提及的猜测、推导或外部知识。
3. 如果【参考资料】中的内容不足以回答用户的提问，或者与提问无关，请直接且礼貌地回答：
   “抱歉，当前知识库中未查询到相关信息。”，切勿瞎编。

# 引用规范
如果资料中包含文件名（File）或页码（Page），请在陈述对应事实的句末加上引用标记，
例如：[参考自：员工手册.pdf_第12页]。

# 【参考资料开始】
{CONTEXT}
# 【参考资料结束】

# 【用户提问】
{QUERY}

# 你的回答：
```

#### 调优技巧

- **结构化隔离**：用 `#`、`【】` 或 XML 标签（如 `<context></context>`）隔开参考资料与用户问题，降低提示词注入影响。
- **多语言对齐**：例如知识库是英文专业文档、用户以中文提问时，加入“尽管参考资料是英文的，但请务必使用流利的中文回答用户”。

## 5. 高级 RAG 架构

### 5.1 Agent Memory

#### 意义

Agent Memory 可视为面向个人用户记忆能力的高级 RAG 演化方向。

#### 与传统 RAG 的区别

| 维度   | 传统 RAG                | Memory                    |
|------|-----------------------|---------------------------|
| 数据来源 | Wiki 知识库、静态文档         | 与用户的对话历史、Agent 反思和行动日志。   |
| 读写特点 | 主要只读                  | 可读可写，随对话动态更新。             |
| 核心目的 | 提供事实性外部知识，弥补 LLM 知识断档 | 维持 Agent 身份连续性、行为习惯和人际关系。 |

### 5.2 GraphRAG

#### 定义与意义

GraphRAG 将知识图谱这一关系网络与传统向量检索结合，使 LLM 能获得更全面的实体关系与全局知识。

#### 传统 RAG 的短板

1. 对全局性总结问题能力有限。
2. 难以跨多层关系推理。
    - 例如用户问“郭靖的师父的师父是谁？”，文档只分别出现“郭靖的师父是洪七公”和“洪七公的师父是 XX”。单纯向量检索可能只命中“郭靖”相关片段，难以顺着关系链跨越中间节点，这类情况可视为“语义断档”。

#### 核心逻辑与工作过程

将非结构化文本转换为**实体（Nodes）— 关系（Edges）— 属性（Properties）**图结构：

1. **离线建图**：借助 LLM 从文档提取人名、公司、技术、概念等实体及其明确关系。
2. **在线双重检索**：
    - Dense Search：检索语义相近的文档切片。
    - Graph Search：定位相关实体节点，顺关系链横向、纵向扩展，取得关联知识。
3. **最终组装**：将关系路径、社区摘要和向量 Chunk 共同放入 Prompt。

#### Microsoft GraphRAG 的两类核心检索模式

- **Global Search（全球化检索）**：面向“这个行业的主要趋势是什么？”等宏观、全局、总结型问题，读取预生成的社区摘要（Community
  Summaries）并做全局归纳。
- **Local Search（局部性检索）**：面向“A 公司某新产品为何影响 B
  公司股价？”等特定实体及复杂关联问题。通过向量命中特定实体，再从图中提取一跳或多跳（Multi-hop）关联节点和线索进行推理。

#### 成本与场景

- **构建成本高**：需要大量 LLM 调用提取实体与关系，API 成本高。
- 适用场景：
    1. 复杂多步推理和关联分析：金融风控 / 反洗钱、法律案件查验、医疗鉴别诊断。
    2. 海量长文本全局总结：深度研报 / 研讯分析、财报 / 长文本审计、网文 / 剧本大纲复盘。
    3. 高度结构化知识的严肃 QA：复杂工业设备 / 航空运维手册、政务与合规条令查询。
    4. 高频更新、实体高度纠缠：企业 360° 客户全景画像、大型软件架构代码分析。

### 5.3 Agentic RAG（智能体化检索增强生成，ReAct 架构）

#### 定义

Agentic RAG 将 LLM 从被动资料查阅者升级为可自主决策、调用工具、自我反思和多轮迭代的 Agent。它以“思考—行动—观察”（Reasoning
Loop）取代固定单次流水线。

#### 能力体现

1. **自主判断是否检索**：如“1+1 等于几”无需检索；专业问题再调用 RAG 工具。
2. **多步拆题与并行检索**：如“对比特斯拉和比亚迪去年的财报毛利率”，可拆成分别检索两家公司财报，甚至调用不同知识库。
3. **自我反思与评估**：检查资料能否完整回答；相关性低或信息缺失时修正关键词，进行第二、第三轮检索。
4. **多样工具调用**：除向量库外，可调用网页搜索获取实时数据，也可调用 Python 等代码执行工具处理报表。

#### 使用场景

研究型任务、复杂合规审计、技术支持 Agent、个性化财务分析等需要反复查证和多方对比的严肃任务。

## 6. 性能、成本与数据新鲜度

### 6.1 Embedding Cache（向量化缓存）

#### 定义与思想

Embedding Cache 是 RAG 或模型推理中的基础降本缓存机制：文本或图片已转换过的向量可复用，遇到**完全相同的输入**直接读取，不再调用
Embedding 模型。

#### 查询端实践

在高并发下，用户频繁搜索“请假流程”“退换货政策”等热门问题时，每次重新嵌入会产生累计 API 成本和约 100–300 ms 的网络 / 推理延迟。可使用内存或 Key-Value 数据库，如 Redis、DiskCache：

- Key：原始文本哈希，例如 `hash("退换货政策")`。
- Value：该文本的 1024 或 1536 维向量数组。

### 6.2 Semantic Cache（语义缓存）

#### 定义和价值

语义缓存使用独立向量库保存历史用户提问和回答。若新问题与历史问题在语义上足够接近，直接返回历史答案，跳过后续 RAG 和 LLM 调用。

传统 Key-Value 缓存不能处理“表达不同、意思相近”的问题；语义缓存尤其适合 To C 产品中高频近义问法的加速和降本。

#### 工作原理

1. 向量化用户提问。
2. 在历史问答向量库做相似度检索。
3. 计算并判断阈值分。
4. 相似度大于阈值时，拦截后续 RAG 与 LLM 调用，直接返回历史生成答案。

#### 参数与淘汰策略

- **相似度阈值**：
    - 过高（如 `0.99`）：退化为近似字面缓存。
    - 过低（如 `0.85`）：可能张冠李戴。
    - `0.95–0.97` 可作为经验起点；该数值必须随嵌入模型、距离度量、领域和缓存对象测试确定。
- **TTL / 淘汰**：天气、最新股价等强时效数据应设置很短 TTL（如数分钟），或通过路由跳过缓存，避免返回过期答案。

#### 开源工具

- **GPTCache**：面向大模型的开源语义缓存框架，支持 Milvus、Qdrant 等向量库和 Redis、SQLite 等标量库后端。
- **RedisVL**：Redis 推出的向量库工具包，提供语义缓存（Semantic Cache）实现。

## 7. RAG 评估

### 7.1 定义

RAG 评估是对检索质量和生成质量做量化验证的工程体系。

### 7.2 三个核心维度

| 指标                                       | 评估方向 | 衡量问题                          |
|------------------------------------------|------|-------------------------------|
| 上下文相关性（Context Relevance）                | 检索阶段 | Chunk 是否包含回答所需线索？无关噪声多不多？     |
| 回答接地性 / 忠实度（Groundedness / Faithfulness） | 生成阶段 | 回答是否完全由检索上下文支持？是否使用外部记忆或编造数据？ |
| 回答相关性（Answer Relevance）                  | 最终体验 | 是否真正回答用户问题、简洁且针对，而不是答非所问？     |

### 7.3 经典指标

- **Hit Rate @ K（命中率）**：标准答案是否存在于前 K 个检索文档中，用于衡量“找得全不全”。
- **MRR（Mean Reciprocal Rank）**：首个正确结果的排位倒数的均值；正确结果越靠前，分数越高，常用于观察排序 / 重排效果。

### 7.4 工业执行流程：LLM-as-a-Judge

1. 构建 Golden Dataset：准备约 100–500 个典型 Query，并为其提供黄金答案（Ground Truth）。
2. 自动化运行 RAG：记录每个问题实际检索到的 Context 与最终 Answer。
3. 裁判模型评分：调用能力较强的模型（如 GPT-4o、Claude 3.5），配合严谨的 Evaluation Prompt，为上述三个维度打分并解释原因。

## 8. 实施注意事项与建议

以下内容用于区分经验参数与通用规律，并提示实施中的准确性、安全性和运维风险。

1. **“向量化实现语义理解”应改为“语义表征与近似匹配”**。Embedding
   能捕捉统计语义关联，但不能可靠地解决全部一词多义、事实判断、否定关系、数值比较或复杂推理；应以离线评测验证目标领域效果。
2. **维度不是越高越好，也不存在统一的“标准型 / 重量级”最优区间**
   。模型训练数据、检索任务、是否可降维、索引和预算共同决定结果。维度翻倍会令原始向量存储和单次距离计算近似线性增长；但“索引时间 /
   消耗指数级增加”并非一般结论。
3. **数据库按“十万 / 百万 / 千万 / 亿级”分档过于绝对**。FAISS
   是库而不是数据库；Chroma、Redis、pgvector、Qdrant、Weaviate、Milvus、Elasticsearch / OpenSearch、Pinecone
   的可用规模均取决于向量维度、过滤比例、召回目标、并发、索引、分片、硬件和运维方式。先用真实数据和 SLA 压测选型。
4. **“Weaviate 图索引优化极佳”容易混淆概念**。Weaviate 的 HNSW 是近邻搜索图索引，不等同于知识图谱 / GraphRAG 的图查询能力。
   `pgvector` 也支持精确检索、HNSW 和 IVFFlat，规模不宜仅由“千万级以下”一刀切判断。
5. **ANN 不是所有场景的默认答案**。数据量小、过滤极强、需可复现的精确召回或评估基线时，Flat / exact search 可能更适合。IVF
   的效果高度依赖训练数据、`nlist` / `nprobe` 等参数，不能简单概括为“边缘向量会漏掉”。
6. **量化压缩率和精度损失不是固定值**。SQ 4×、FP16 2×、1-bit BQ 32×是典型存储量级，但 PQ / OPQ / RVQ 的比率和“损失
   5%–15%”需看维度、码本、数据分布、距离指标和是否重排。BQ 对高维、分布合适的模型更友好，通常要配合 oversampling / 原始向量重评分。
7. **相似度、Reranker 分数不存在跨模型通用阈值**。`0.85` 向量分、`0.5` 重排截断、`0.05` 拒答和语义缓存 `0.95–0.97`
   都只能作为实验起点；余弦、点积、归一化方式以及模型均会改变分布。应以标注集绘制 precision-recall / 风险—覆盖曲线后定阈值。
8. **Reranker 不能保证“绝对相关性分数”**。不少重排模型输出的是模型特定打分或 logit，未必是已校准的 0–1
   概率；应校准、观察分桶表现，并在拒答判断中结合检索证据、问题类型和业务风险。
9. **“只能依据上下文回答”的 Prompt 不能单独防止幻觉或提示词注入**
   。参考资料本身可能不完整、相互冲突或含恶意指令。建议把资料当不可信数据，明确“忽略资料内指令”，实施内容清洗、权限过滤、引用粒度校验和回答后验证。
10. **邻居扩展会扩大噪声和权限暴露面**。需要以 `document_id + chunk_position` 稳定定位邻居；先做与命中 Chunk 相同的租户 /
    ACL / 版本过滤，并设置最大扩展数和 Token 预算。短块、高分或连接词只是启发式信号。
11. **父子检索的优点表述需要更精确**。子块主要提高定位粒度，不天然保证 Recall；父块主要提升上下文完整性，也可能引入噪声并撑爆窗口。应对同一
    `parent_id` 去重，按预算截断，并比较“子块直送 / 邻居扩展 / 父子块”三种方案。
12. **GraphRAG 不应被视为传统 RAG 的普遍替代**。它在跨实体关系和全局主题归纳上有价值，但实体 /
    关系抽取错误会传播，建图与更新成本高。Microsoft GraphRAG 当前还包含 Basic、Local、Global、DRIFT 等不同查询方式，使用前应进行成本收益验证。
13. **医疗、金融、法律示例须额外控制风险**。这些领域不能把 RAG 命中或 GraphRAG 推理直接当成专业结论；需要权威数据源、时效控制、人工复核、审计记录和合规流程。
14. **MD5 不适合作为安全完整性校验**。它可作为非安全的变更检测键，但对于可信校验或攻击面场景，建议使用 SHA-256
    等抗碰撞摘要；同时记录规范化规则、Embedding 模型版本、Chunking 版本和删除墓碑，避免重复与陈旧索引。
15. **Embedding Cache 与 Semantic Cache 的键必须包含版本和作用域**。至少纳入模型 / 维度、归一化 / 预处理版本、租户 /
    权限、语言、系统提示词、知识库版本和 TTL。缓存命中前还要检查权限、引用和时效，不能将一个用户答案直接复用给无权限用户。
16. **评估不能只依赖 LLM 裁判**。LLM-as-a-Judge 高效但有偏差、成本和不稳定性。应保留人工标注集、引用正确性 /
    覆盖率、拒答正确率、延迟、成本、失败率与线上反馈；用固定裁判模型和 Prompt 版本做回归比较。
