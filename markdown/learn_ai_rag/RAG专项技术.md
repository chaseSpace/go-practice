# RAG专项技术
## 邻居扩展
### 说明
- 一种优化技术，解决检索到的chunk不包含完整上下文的问题（最终导致提供给LLM的预料不完整）
### 核心方案
- 向量检索定位 + 物理索引还原
### 触发时机（满足条件）
- A. 基于召回文本的“语义连贯性”判定
  - 1. 句式判断
    - 1.1 问步骤、前提、原因、对比：通常需要完整上下文
      - containsAny(query, "如何", "步骤", "前提", "为什么", "原因", "区别", "优缺点")
    - 1.2 本段以指代、连接词开头：上文可能定义了“它/该/上述”的对象
      - startsWithAny(text, "然后", "因此", "此外", "但是", "该", "此", "上述", "它", "this", "however")
    - 1.3 本段结尾像未结束的列表、句子、代码或条件：下文可能包含结论
      - endsWithAny(text, "：", ",", "，", "(", "（", "{", "```")
  - 2. 长度判断
    - chunk 很短，常是标题、列表项或边界残片
      - utf8.RuneCountInString(text) < 120
- B. 基于 Query 的类型判定
  - 高触发意图
    - 当用户提问属于流程类、因果推理类、长篇故事线（例如：“XX事件的前因后果是什么？”、“这个操作的具体步骤是什么？”）。这类任务天然需要连续的上下文
  - 低触发意图
    - 当用户提问属于事实型、短实体检索（例如：“周杰伦的生日是哪天？”、“特定产品的型号是什么？”）。这种情况下闭环语义即可满足，不触发扩展
- C. 基于检索分数的边界判定
  - 当核心 Chunk 的向量相似度得分极高（说明方向绝对正确），但该 Chunk 长度较短时，可自动触发邻居扩展
## 向量化
### 本质
- 将**文本或媒体**转化为高维空间中的一组数字（向量），实现了语义理解。
### 作用
- 1. 核心作用：将“文本”转化为“语义坐标”
  - 1.1 语义相近，空间距离就相近—— 在向量空间中，“猫”和“狗”的距离会比“猫”和“汽车”的距离更近。
  - 1.2 解决一词多义与同义词问题—— 它能识别出“电脑”和“计算机”表达的是同一个东西；也能根据上下文区分“苹果”是指水果还是手机品牌。
- 2. 在 RAG 中的关键角色：实现高效的“语义检索”
  - 2.1 统一表达：它把用户的提问（Query）和知识库里的文档块（Chunks）都转化到同一个高维向量空间中。
  - 2.2 快速筛选：通过计算数学上的向量相似度（如余弦相似度），计算机可以在毫秒级内从百万级的文档中，找出与用户提问语义最相关的 Top-K 个文档片段，作为大模型的“参考资料”。
- 3. 多模态桥梁：连接不同的数据类型（文本、图片、音频）
  - 3.1 可以将文字、图片、音频甚至视频映射到同一个向量空间。这使得系统可以实现“用文字搜索图片”（输入“奔跑的马”，检索出马的图片）
### 技术关键词
- Embedding / 向量化
  - 维度
    - 代表了向量空间中独立坐标轴的数量。如果把一个向量看作一个人的“画像”，那么维度就是用来描述这个人的“特征标签数量”（如身高、体重、职业、爱好等）。—— 数据源向量化的维度（所用向量模型决定） 和 向量化DB定义的维度 必须一致
    - 维度的多少直接平衡了模型的理解能力（表达精度）与计算的开销（性能成本）。
      - **高维度（如 1536, 3072）**：意味着模型有更多的“空间”去捕捉文本中极其微妙的语义差别、语气、上下文背景和专业术语。
      - **低维度（如 256, 384）**：特征空间较小，只能捕捉最核心、最粗颗粒度的语义信息，容易丢失细节。
    - 直接影响计算速度与存储成本（性能）
      - 向量的维度每增加一倍，向量数据库的内存/显存占用、索引建立时间以及相似度计算的耗时都会线性或指数级增加。
    - 根据场景选择
      - ——轻量级 (384 - 768)速度极快，省内存，但处理复杂长文本能力较弱。
        - 手机端本地部署、Q&A 问答对匹配、预算及内存极度受限的场景。
      - ——标准型 (1024 - 1536)性价比最高，在语义准确度和计算性能之间达到了完美的平衡。
        - 通用 RAG 最推荐。企业知识库、文档检索、客服机器人。
      - ——重量级 (3072 及以上)语义捕捉最精准，但极其消耗内存和计算资源。
        - 法律条文对比、医疗病历检索、深度学术论文分析。
- Embedding 模型
  - 作用
    - LLM厂商提供，维度确定，提供给开发者使用。将数据源进行向量化
  - 关注参数
    - 维度—— 输出向量的数字长度
    - 最大输入 Token 限制—— 单次输入给模型进行向量化的文本最大长度。
    - 检索相关指标
      - NDCG@10 / NDCG@5：衡量检索出的前 5 或 10 个结果的排序质量，越相关的结果越靠前，分值越高。这是 RAG 最核心的指标。
      - Hit Rate (命中率)：标准答案是否存在于检索出的 Top-K 结果中。
    - 语言与领域支持度
      - 模型是单语（如仅中/英）还是多语（Multilingual）
    - 调用成本 (Cost)
      - 通常按每百万 Token 计费（以 OpenAI text-embedding-3-small 为例，大约 $0.02 / 1M tokens）。
- Chunk（分块）
  - 作用
    - 将较大的数据源以某种策略 切分 成多个块，再向量化。—— 如果切分混乱，将连贯的上下文切开，会导致检索效果变差。
  - Chunk Size
  - Chunk Overlap
    - 作用：避免信息刚好被切断。
  - Chunking 策略
    - 定长，效果差
    - 递归分块，是一种目前常用且效果较好的分块策略
      - 它的核心思想是：“大化小，层层递进”。它使用一组有优先级的分隔符（如段落、换行、句号、空格），递归地将长文章切分成大小合适、且尽可能保持语义完整的小块（Chunks）。
      - 切分逻辑
        - 0. 配置一个分隔符列表（Separators）：\n\n；\n；空格；空字符
        - 1. 尝试用最高优先级的分隔符（如 "\n\n"）把整篇文章切开。
        - 2. 检查切开后的每一个小块。如果某个小块的长度小于你设定的最大目标（比如 500 Token），它就会被保留，不再切分。
        - 3. 如果某个小块的长度大于了 500 Token，算法就会对这个小块降级使用下一个分隔符（如 "\n"）继续切分。
        - 4. 以此类推，直到所有的小块都符合长度限制。
    - 语义化分块，需要模型辨别
    - 结构化分块，例如针对MD文档，直接基于标题切分更好
- Metadata（元数据）
  - 本质
    - 元数据（Metadata）是与向量数据绑定存储的结构化键值对（Key-Value Pairs）。
  - 作用
    - 向量检索时对向量匹配的数据进一步过滤（参数来自搜索条件），以上权限隔离/引用溯源/时效性排序/一些高级检索策略如父子块检索
  - 分类
    - 文档溯源属性
      - source_id / doc_id：原始大文档的唯一 ID
      - file_name / file_path：原始文件名或存储路径（如 s3://bucket/docs/policy.pdf）。
      - page_number：该分块源自 PDF 或 Word 的第几页。
      - url：如果是网页爬取的数据，记录原始链接。
    - 内容结构属性
      - chunk_id：当前分块的唯一自增 ID。
      - parent_id：如果使用了父子块检索（Parent-Child Retrieval），记录其所属大段落（Parent Chunk）的 ID。
      - heading / section：该分块所属的章节标题（如 ### 第三章 薪酬福利）。
    - 业务管理与权限属性
      - category / tag：业务分类（如 HR、财务、技术文档）。
      - user_id / tenant_id：用户 ID 或租户 ID（在多租户 SaaS 架构中极其重要）。
      - access_level / role：权限等级（如 admin、public、internal），防止越权访问。
    - 时效性属性
      - created_at / updated_at：文档的创建或最后更新时间戳。
      - version：文档版本号（如 v1.0，v2026_Q1）。
- Vector DB（向量数据库）
  - 十万内
    - Chroma
    - FAISS
  - 百万级以内
    - Redis，受限于内存成本
  - 千万级至亿级
    - Qdrant，Rust 编写，单机性能极高且支持分布式
    - Weaviate：Go 编写，图索引优化极佳，支持云端与分布式部署。
    - pgvector：PostgreSQL 插件，生态极佳，随主库性能扩展，适合千万级以下。
  - 亿级以上
    - Milvus：存算分离，专为百亿级海量向量设计的专业分布式数据库
    - Elasticsearch / OpenSearch：成熟的分布式引擎，海量文本与向量混合检索首选。
    - Pinecone：云原生全托管（SaaS），后台自动扩容，免运维承载海量数据。
- 快速检索算法
  - ANN：近似最近邻搜索
    - 定义：它不是某一种具体的算法，而是一类“用精度换速度”的搜索技术总称（技术分类）。
    - 具体算法
      - HNSW：分层可导航小世界图
        - 基于“图（Graph）结构”的 ANN 算法，是目前 RAG 领域最主流、最核心的索引方式。
        - 优点：检索速度极快，准确率（命中率）极高。
        - 缺点：因为要在内存中维护复杂的图结构，非常消耗内存（RAM）。
        - 使用场景：预算充足，追求高召回率的 RAG 标配
      - IVF：倒排文件索引
        - 原理：基于“聚类（Clustering/分组）”
        - 优点：不需要建复杂的图，内存占用非常小，省钱。
        - 缺点：如果目标向量刚好落在格子的边缘，容易被漏掉，因此准确率和极端性能不如 HNSW。
        - 使用场景：数据量极大（亿级以上），内存预算有限
- 向量数据压缩算法
  - 作用
    - 降低大规模数据占用的体积（磁盘或内存）
  - PQ：Product Quantization（乘积量化）
    - 子主题
  - 所有压缩算法
    - 无压缩 (FP32)—— 内存消耗最高，精度最高
    - 半精度 (FP16)—— 2x压缩，硬件支持GPU加速、需兼顾高精度的场景
    - SQ (标量量化)—— 4x压缩，绝大多数通用RAG生产环境（性价比最高），准确率损失极小(<1%–2%)
    - BQ (二进制量化) —— 32x压缩，适合海量数据第一轮超高速粗筛（需配合重排）
    - PQ (乘积量化)—— 16x - 64x压缩，亿级以上海量数据、内存预算极度受限。准确率损失5%-15%
    - OPQ (优化乘积)—— 16x - 64x压缩，数据维度关联性强、追求高召回率的超大规模库。准确率损失小于PQ
    - RVQ (残差量化)—— 16x - 64x压缩，深度学习高级索引、多级向量检索方案
  - 工业级做法
    - 为了兼顾低成本（省内存）与高精度（不丢语义），现代向量数据库（如 Qdrant、Milvus）通常不单用某一个算法，而是采用组合拳：两阶段检索
      - 两阶段检索（Rescoring）：在线上运行时，先用 SQ8 或 BQ 压缩向量在内存中快速跑出 Top-100（粗筛），然后将原始的 FP32 向量存在硬盘（不占内存），对这 100 个结果做精准重排（精筛）。
- Top-K Retrieval
  - 说明：是指从数据库的所有候选数据中，找出与用户提问（Query）最相关的、前 K 个结果的过程。
  - 执行过程
    - 以 RAG 场景为例，Top-K 检索的运行逻辑非常简单直观
    - 1. 向量化提问：用户输入问题（Query），系统通过 Embedding 模型将其转化为一个向量。
    - 2. 计算相似度：向量数据库计算这个 Query 向量与库里所有文档块（Chunks）向量之间的数学距离（如余弦相似度）。
    - 3. 排序与截取：数据库将所有文档块按照相似度得分从高到低排序，然后截取得分最高的前 K 个片段返回。
  - 意义
    - K 值的大小是调优 RAG 系统性能和准确率的核心关键参数
    - 当 K 值设置得较小（如 K = 2 或 3）
      - **优点：**给大模型（LLM）输入的上下文非常精简，生成速度快，API 费用便宜。同时，减少了无关噪声的干扰。
      - **缺点：**如果用户的提问比较复杂，需要参考多处文档，较小的 K 值可能会漏掉核心答案（召回率不足），导致大模型无法完整回答。
    - 当 K 值设置得较大（如 K = 15 或 20）
      - **优点：**几乎把所有可能相关的资料都捞出来了，答案的命中率（Hit Rate）非常高。
      - **缺点：**塞给大模型的数据量暴增，导致 LLM 推理变慢，Token 成本大幅上升。更严重的是，过多的无关信息（噪声）会干扰大模型，导致它在长文本中迷失（即著名的“Lost in the Middle”现象），反而降低回答质量。
- Recall（召回率）
  - 作用
    - 是衡量系统“找得全不全”的核心指标。
  - 计算公式
    - 检索出的相关doc数量  / 实际存在的全部相关doc数量
  - 如何提高
    - 增大 Top-K 值：从粗筛中返回更多的分块（如从 Top-5 改为 Top-20）
    - 引入混合检索（Hybrid Search）：同时使用向量检索（抓取语义相关的）和传统的 BM25 关键词检索（抓取含有一模一样产品型号或人名的），防止向量模型出现语义偏差而漏掉关键词。
    - 优化分块策略（Chunking）：使用 Recursive Chunking 并设置合理的 Overlap（重叠度），防止核心答案因为被切成两半而导致向量化后特征不明显。
- Keyword Search / BM25
  - 作用
    - 一种基于字面完全匹配的传统检索技术。
  - 意义
    - BM25（Best Matching 25） 是目前工业界公认最经典、效果最好的关键词检索打分算法（它是著名的开源搜索引擎 Elasticsearch 和 Lucene 的底层核心算法）
    - 弥补向量化查询准确率不足的问题。向量化的缺点是 遇到冷门产品型号、长代码块、特定专有名词时容易泛化失效。
  - 工业级做法：双路并发
    - 向量检索——获取语义相关的 Top-50
    - BM25 检索—— 获取字面精准的 Top-50
    - 合并后 ——► Reranker (重排) ──► 最终 Top-5
- 混合检索融合算法
  - 定义：一种算法将向量检索和BM25检索的结果集合并出新的 Top 50（示例）
  - 所有算法
    - RRF (倒数排名)
      - 复杂度低，性能高，准确率稳定。适合通用 RAG 项目。
    - 线性加权 (MinMax)
      - 复杂度低，性能高，准确率由权重而定。适合在两个通道分数分布极其稳定的简单场景
    - Reranker (重排模型)
      - 复杂度高（需要使用单独模型），准确率高。企业级、生产级 RAG 系统的最终标配
- Rerank
  - 定义
    - 将首次向量化检索的Top K结果集 和 问题一起送入专门的重排模型，进行二次相关性排序，最后再截取Top 5（示例）
  - 解决痛点
    - 1. 解决“大模型在长文本中迷失” —— 粗筛的Top 50结果太多，直接塞给LLM会导致其只能记住前面和结尾的信息，忽略中间的信息。Rerank能够将最高质量答案排在最前面，大幅提高回答准确率
    - 2. 过滤无关垃圾（设置绝对置信度分数）—— 向量检索算出的相似度（如 0.85）在更换模型后就没有参考价值了，且经常出现“矮子里拔将军”的现象。成熟的Rerank模型会输出一个具有强业务参考价值的绝对相关性得分（0~1），如果重排后的第一名chunk得分只有0.05，那么系统可以直接舍弃全部chunk，直接回答“知识库中查无此项”，防止瞎编（幻觉）。
  - 选择重排模型
    - 选择低成本模型 + 恰当的提示词 即可
    - 也有推荐的rerank模型：bge-reranker-v2-m3；这种模型不需要提示词，有专业接口支持，API直接返回一个相关性分数
- Query Rewrite
  - 定义
    - 在把用户的提问送去向量库检索之前，先对用户的原始提问进行“加工、润色或拆解”，从而让计算机更准确地理解用户的真实意图。
  - 背景
    - 1. 多轮对话中的指代不明（缺乏上下文）
      - 第一句：周杰伦是谁；第二句：它有多少专辑；—— 这里第二句直接放入向量DB检索会导致结果混乱。
    - 2. 用户提问太简短或太口语化
      - 用户提问：“高血压吃啥药？”—— 但企业医疗知识库中可能有很多高血压相关的各类疾病，吃的药物也不同。也会导致结果混乱。
    - 3. 一句话里包含了多个问题
      - 用户提问：“对比一下 iPhone 16 和 15 的续航，顺便把价格也发我。”—— 这是一道“复合题”。单一的向量检索很难同时兼顾“16续航”、“15续航”、“16价格”、“15价格”四个维度的文档匹配。
  - 实现
    - 在实际工程中，通常会通过调用一个便宜且速度快的小大模型（LLM）加上特定的提示词，来实现以下几种重写策略。
      - 1. 核心提炼与去噪
        - 去掉用户话语中的语气词和废话，补全多轮对话中的代词。
      - 2. 扩展/生成多个同义句
        - 让大模型根据用户的一个问题，从不同角度生成 3~5 个意思相同但措辞不同的新问题。
      - 3. 假设性文档生成
        - 让大模型先针对用户的问题盲猜（生成）一个虚构的、不一定准确的答案，然后拿着这个虚构的答案向量化去库里检索。
- 父子文档检索
  - 作用
    - 一种专为解决 RAG 系统中“检索精度”与“大模型上下文完整度”天然矛盾而设计的高级文本切分与检索策略。
  - 背景
    - 在传统的 RAG 中，你必须做一个两难的决定：—— 1. 切小块，模型容易命中，但缺少上下文—— 2. 切大块，语义稀释，会降低检索命中率
  - 实现
    - 该策略在数据入库和检索时，将整个过程分为了两个完全独立的层级。
      - 1. 数据准备阶段（大包小）
        - 定义父文档（Parent Docs）：首先将原始长文章切分成较大的段落（例如，按章节切分，每块 1000–2000 字）。
        - 定义子文档（Child Chunks）：在每一个父文档内部，进一步切分成更小的细粒度切片（例如，每块 150–200 字）。
        - 建立映射存入数据库
          - 1. 向量数据库：只对“子文档”进行向量化（Embedding）并存入。 同时，在每个子文档的 Metadata（元数据） 里记录它所属的 parent_id。
          - 2. 关系库/内存键值库（Docstore）：将完整的“父文档”原始内容以 parent_id 为键存在这里，不占用昂贵的向量库显存。
      - 2. 在线检索阶段（用小捞大）
        - 用户提出问题，系统去向量数据库里检索。
        - 因为子文档颗粒度小，核心语义集中，向量模型能够极度精准地命中最相关的 3~5 个子文档（Child Chunks）。
        - 关键一步：系统不把这些零碎的子文档直接喂给大模型。而是读取它们 Metadata 中的 parent_id。
        - 系统顺藤摸瓜，去 Docstore 里直接捞出对应的、包含完整上下文的“父文档”（Parent Docs）。
        - 最终，把这些内容完整、逻辑连贯的父文档塞进 Prompt 喂给大模型。
  - 核心优势
    - 检索准确率与生成质量兼得：子文档保证了向量检索的高召回率（Recall）；父文档保证了大模型理解语境的高准确率（Precision）。
- Context Window 管理
  - 意义
    - 是直接决定系统运营成本（Token 费用）、响应速度（延迟）和回答质量的关键工程环节点。
  - 如何进行
    - 1. 动态token预算分配
      - 可用检索上下文 = 最大窗口 - 系统提示词 - 历史聊天记录 - 预期输出空间
      - 不能简单按字数算，必须使用对齐的 Tokenizer（如 OpenAI 的 tiktoken）在代码端实时计算。
    - 2. 检索内容的动态漏斗与过滤
      - 2.1 Reranker 分数截断
        - 对重排后的TopK内容再次过滤 > 0.5的内容，其他内容丢弃
      - 2.2 信息密度压缩 (如 LLMLingua 算法)
        - 在文档喂给大模型之前，先用一个轻量级模型计算文档中哪些词是“废话”，定向剔除文本中的助词、冗余格式和重复表述。通常可以在不损失核心语义的前提下，将 Context 压缩 2x 到 5x
    - 3. 历史聊天记录的剪枝策略（压缩）
      - 3.1 滑动窗口法
        - 最简单常用。只保留最近的 N 轮对话
      - 3.2 总结摘要法
        - 让一个便宜的小模型定期对久远的聊天历史进行一句话摘要。窗口中只保留：[长期历史摘要] + [最近2轮详细对话] + [当前检索到的RAG资料]。
    - 4. 优化“迷失在中间”的物理排列
      - 说明：大模型对 Context Window 开头（Head）和结尾（Tail）的信息最为敏感，而放在中间（Middle）的信息极易被模型忽视。
      - 采用两头重、中间轻的排列策略
        - 将 Reranker 分数最高的、最绝对相关的文档，放在最前边和最后边，把相关性稍弱的文档挤在中间。这样可以最大化利用大模型的注意力机制，提高回答准确率。
- RAG Prompt
  - 定义
    - 是 RAG 系统中发送给大模型（LLM）的最终核心指令模板。
  - 作用
    - 提示LLM只能按照检索到的资料来回答问题，如没有检索到则回答知识库没有结果。
  - 标准实践
    - 一个优秀的、能在生产环境稳定运行的 RAG Prompt 模板通常包含以下 4 个黄金板块
      - 1. 角色与人设定位—— 提升回答的专业度和语气规范
        - “你是一位严谨的企业知识库AI助手……”
      - 2. 考场纪律与边界限制—— 防止大模型产生“幻觉（胡说八道）”的最终防线
        - “请严格根据提供的【参考资料】回答问题。如果参考资料中没有提及相关信息，请直接回答‘抱歉，知识库中未记载相关内容’，绝对不允许凭空捏造或利用你自身的知识储备进行发挥。”
      - 3. 动态插值槽—— 将检索结果和用户提问精准填入模板指定位置
        - “【参考资料】：{CONTEXT}”“【用户提问】：{QUERY}”
      - 4. 输出格式与引用要求—— 要求大模型在回答时标明出处（来自Metadata）
        - “如果你的回答引用了参考资料，请在句末使用 [文档名_页码] 的格式进行标注。”
    - 示例
      - # 角色你是一位专业、严谨的企业内部知识库问答助手。# 核心指令（考场纪律）1. 请仔细阅读下方提供的【参考资料】，并仅根据这些资料回答用户的【提问】。2. 你的回答必须完全忠实于参考资料，不得包含任何资料中未提及的猜测、推导或外部知识。3. 如果【参考资料】中的内容不足以回答用户的提问，或者与提问无关，请直接且礼貌地回答：“抱歉，当前知识库中未查询到相关信息。”，切勿瞎编。# 引用规范如果资料中包含文件名（File）或页码（Page），请在陈述对应事实的句末加上引用标记，例如：[参考自：员工手册.pdf_第12页]。# 【参考资料开始】{CONTEXT}# 【参考资料结束】# 【用户提问】{QUERY}# 你的回答：
  - 调优进阶技巧
    - 结构化隔离
      - 使用类似于 # 标签、【】 符号或 XML 标签（如 <context></context>）将参考资料和用户提问死死隔开。尽量避免提示词注入
    - 多语言对齐
      - 如果你的知识库里全是英文专业文档，但用户用中文提问，可以在 Prompt 里加入：“尽管参考资料是英文的，但请务必使用流利的中文回答用户。”
- Agent Memory
  - 意义
    - 是高级 RAG 的进化体（实现个人用户的记忆能力）。
  - 与传统RAG区别
    - 1. 数据来源不同
      - 传统RAG的数据来源是 wiki知识库 和 静态文档
      - Memory的数据来源是与用户的对话历史，Agent反思和行动日志
    - 2. 读写特点不同
      - 传统RAG 是只读。
      - Memory 是可读可写，跟随对话动态更新
    - 3. 核心目的
      - 传统RAG 是提供事实性的外部知识，防止 LLM 知识断档。
      - Memory 是维持智能体自身的身份连续性、行为习惯与人际关系。
- GraphRAG
  - 定义
    - 是一种将关系型网络（知识图谱）与向量检索（传统 RAG）强强联合的高级检索增强技术。
  - 意义
    - 让LLM能看到一张全景知识关系网，回答问题时会更全面
  - 背景
    - 传统 RAG 的致命短板
      - 1. 缺乏全局总结能力（全局性提问）
      - 2. 无法跨多层关系进行推理
        - 例如 “郭靖的师父的师父是谁？”，而文档里可能只有“郭靖的师父是洪七公”和“洪七公的师父是XX”。—— 输入 Query 后，向量只能匹配到“郭靖”，无法直接跨越中间节点去检索到“师父的师父”，这在数学上叫语义断档。
  - 核心逻辑
    - 将非结构化文本转化为“实体（Nodes）- 关系（Edges）- 属性（Properties）”的图结构
  - 工作过程
    - 1. 离线建图阶段（文本 ➔ 知识图谱）
      - 借助大模型（LLM）提取文档中的所有实体（如：人名、公司、技术、概念）以及它们之间的明确关系
    - 2. 在线检索阶段（双重打捞）
      - 当用户提问时，系统会进行二维检索
        - 1. 向量维度（Dense Search）：寻找语义相近的文档切片（和传统 RAG 一样）。
        - 2. 图谱维度（Graph Search）：寻找与问题相关的核心实体节点，顺着“骨架（关系链）”横向和纵向延伸，把一整张关系网上的关联知识全部打捞上来。
      - 最终组装：将关系路径、社区摘要和向量分块一起拼接进 Prompt，喂给大模型。
  - Microsoft GraphRAG 的两种核心检索模式
    - 全球化检索
      - 回答宏观、全局、总结性的提问（如“这个行业的主要趋势是什么？”）。—— 直接无视具体的碎纸片，去读取知识图谱中预先生成的各个“社区摘要（Community Summaries）”，进行全盘总结。
    - 局部性检索
      - 回答涉及特定实体及其周边复杂关联的具体问题（如“A 公司的某个新产品为何会影响到 B 公司的股价？”）。—— 通过向量命中特定实体，再从图谱中提取该实体周围“一重或多重（Multi-hop）”的所有关联节点和线索，进行精准推理。
  - 构建成本
    - 极高。需要调用大量 LLM 推理来提取实体和关系，非常烧 API 费用。
  - 使用场景
    - 1. 复杂多步推理与关联分析—— 金融风控&反洗钱—— 法律案件查验—— 医疗鉴别诊断
      - 当答案无法在一处文档中直接找到，而是需要像破案一样“顺藤摸瓜”，跨越多个实体和事件进行关联时。
    - 2. 海量长文本的全局宏观总结—— 深度研报/研讯分析—— 财报/长文本审计—— 网文/剧本创作大纲复盘
      - 当用户提出的问题不是“某一点的具体事实”，而是涉及整本书、整个项目或全量数据库的全局性全局观问题时。
    - 3. 专业领域具有高度结构化知识的严肃 QA—— 复杂工业设备/航空运维手册—— 政务与合规条令查询
      - 在一些专有名词极多、概念之间等级和依属关系极其严谨的行业，传统向量检索极易因为“语义泛化”而混淆概念。
    - 4. 数据高频更新与强实体纠缠的场景—— 企业 360° 客户全景画像—— 大型软件架构代码分析
      - 如果你的数据集是围绕特定的“核心实体”（如特定客户、特定代码模块、特定产品）展开，且这些实体之间在不断产生新的动态关系。
- Agentic RAG（智能体化检索增强生成，ReAct 架构）
  - 意义
    - 将大模型（LLM）从一个“被动的资料查阅者”升级为了一个“拥有自主决策、工具调用、自我反思和多轮迭代能力的智能代理（Agent）”。
  - 与传统RAG的不同
    - 在传统 RAG 中，流水线是死板且线性的（用户提问 ➔ 检索 ➔ 组装 ➔ 生成回答）。如果第一次检索出的资料不够好，大模型也只能将错就错。
    - Agentic RAG 打破了这种线性限制，引入了“思考-行动-观察”的自主循环（Reasoning Loop）
  - 聪明在哪里
    - 1. 自主判断是否需要检索
      - “1+1等于几” 不需要检索。—— 只有遇到专业问题时，它才会自主决定“我要调用 RAG 工具去查档案”。
    - 2. 多步分拆与并行检索
      - 面对复杂问题（如“对比特斯拉和比亚迪去年的财报毛利率”），它不会直接用整句话去检索，而是把任务拆解为“检索特斯拉财报”和“检索比亚迪财报”两个独立动作，甚至可以同时调用不同的知识库。
    - 3. 自我反思与评估
      - 拿到检索结果后，Agent 会自己先读一遍，扮演“质检员”：“这些资料真的能完整回答用户的问题吗？”。如果发现相关性太低或有信息缺失，它会自动修正搜索关键词，开启第二轮、第三轮检索，直到满意为止。
    - 4. 多样化工具箱
      - 它不仅能检索文本向量库。如果发现问题需要实时数据，它可以选择调用“谷歌网页搜索工具”；如果需要算力，它可以调用“Python 代码执行工具”去算个报表。
  - 使用场景
    - 适合用于**研究型任务、复杂合规审计、技术支持Agent、个性化财务分析**等需要反复查证、多方对比的严肃场景
- RAG 评估
  - 定义
    - 是对检索增强生成系统（RAG）的检索质量和生成质量进行量化评测的工程体系。
  - 三元组
    - 上下文相关性 (Context Relevance)
      - 评估方向：检索阶段（找得准不准）。
      - 衡量标准：检索出来的文档片段（Chunks）中，水分多不多？是否包含回答用户问题所需的关键线索？是否夹带了大量无关的垃圾信息？
    - 回答接地性/忠实度 (Groundedness / Faithfulness)
      - 评估方向：生成阶段（有没有瞎编/幻觉）。
      - 衡量标准：大模型生成的回答，是不是百分之百基于检索到的上下文？如果大模型使用了自己原本的记忆去回答，或者凭空捏造了上下文里没有的数据，这项得分就会极低。
    - 回答相关性 (Answer Relevance)
      - 评估方向：最终体验（有没有答非所问）。
      - 衡量标准：最终的回答是否真正切中了用户的提问？是否简洁、针对性强，而不是长篇大论却顾左右而言他。
  - 经典指标
    - Hit Rate @ K (命中率)
      - 标准答案是否存在于检索出的前 K 个文档中（衡量找得全不全）。
    - MRR (Mean Reciprocal Rank)
      - 标准答案在检索结果中的排位。排位越靠前，说明重排（Rerank）效果越好。
  - 工业界是如何执行评估？—— 让大模型做裁判
    - 1. 构建测试集（Golden Dataset）—— 准备 100~500 个典型的用户问题（Query），并配有标准的黄金参考答案（Ground Truth）。
    - 2. 自动化流水线—— 运行 RAG 系统，记录系统在每个问题下实际检索到的 Context 和生成的 Answer。
    - 3. 裁判模型打分—— 调用一个高智商的大模型（如 GPT-4o 或 Claude 3.5），配合极其严谨的评估提示词（Evaluation Prompts），让它扮演裁判，对上述的“三元组”指标进行逐一打分和原因分析。
- Embedding Cache（向量化缓存）
  - 定义
    - 是 RAG 系统或大模型推理中用于降本增效的一种基础缓存机制。
  - 核心思想
    - “计算一次，到处复用”。既然将文本、图片转化为高维向量需要消耗 API 费用和计算时间，那就把计算过的结果存起来，下次遇到完全一样的输入时直接读取，不再重新调用模型。
  - 实践
    - 1. 查询端缓存—— 降本、提速
      - 当用户在高并发场景下频繁搜索某些热门关键词（如“请假流程”、“退换货政策”），系统每次都要把这些词传给 OpenAI 或本地模型转成向量，会产生累计 API 费用和 100~300ms 的网络/推理延迟。
      - 解法
        - 通过内存或 Key-Value 数据库（如 Redis、DiskCache）搭建一层缓存。
        - Key：用户输入的原始文本的哈希值（如 hash("退换货政策")）。
        - Value：该文本对应的 1024 或 1536 维向量数组。
- Semantic Cache（语义缓存）
  - 定义
    - 使用一个独立的向量库来缓存用户提问，从而快速提取已有的历史回答作为回复。免去后续的RAG+LLM调用
  - 背景
    - 传统的键值对DB无法处理语义相近的提问查询，只有向量DB可以。而语义相近的查询对to C产品是高频事件，对此类查询可以提速降本。
  - 工作原理
    - 1. 将用户提问向量化
    - 2. 在【历史问答向量数据库】中进行相似度检索
    - 3. 计算阈值分
    - 4. 如果相似度得分大于设定的阈值，说明两句话是一个意思，系统直接拦截后续的所有 RAG 和大模型调用，把历史上大模型生成过的文本答案直接甩给用户
  - 核心参数与调优指南
    - 1. 相似度阈值
      - 设得太高（如 0.99）：语义缓存退化成普通字面缓存。
      - 设得太低（如 0.85）：产生严重的张冠李戴错误
      - 工业界黄金值：通常经过多轮测试后，卡在 0.95 ~ 0.97 之间。
    - 2. 缓存淘汰策略与 TTL
      - 对于时效性极强的数据（如“今天的天气”、“公司最新的股票价格”），语义缓存的 TTL 必须设置得很短（如几分钟），或者干对这些路由实行缓存穿透（不走缓存），防止用户拿到过期的错误历史答案。
  - 开源工具
    - GPTCache
      - 目前最著名的、专门为大模型定制的开源语义缓存独立框架，支持配置各种向量库（Milvus, Qdrant）和标量库（Redis, SQLite）作为后端。
    - RedisVL
      - Redis 官方推出的向量库工具包，里面内置了极为强大的语义缓存（Semantic Cache）标准实现。
- 增量索引
  - 作用
    - 当数据源变化时，只对改变的部分文档进行处理，包括增删改的部分
  - 状态追踪机制
    - 哈希校验法（常用）
      - 对原始文档和它的chunk进行MD5跟踪
    - 时间戳/版本号轮询
      - 依赖源系统的 updated_at 时间戳或版本字段。每次同步时，只向源数据库捞取 updated_at > Last_Sync_Time 的数据。
    - CDC (Change Data Capture，变更数据捕获)
      - 如果你的 RAG 数据源是关系型数据库（如 MySQL、PostgreSQL），可以直接监听数据库的 Binlog 日志。
## Chunking
### 作用
- 语义聚焦：提升向量检索的精准度
  - 例如将大文档拆成 200 字的小块，让每一个 Chunk 的语义高度聚焦在某一个具体的话题上
- 突破大模型的上下文窗口限制
  - 通过 Chunk 化的检索，只把与问题最相关的、加起来不到几千字的 3-5 个 Chunk 喂给大模型，化整为零，确保大模型能装得下、读得完。
- 节省计算成本与提升响应速度
  - 大模型的计费和推理延迟（TTFT）与输入的 Token 数量成正比
- 减少幻觉回答
  - 如果信息藏在一段极长文本的中间部分，大模型很容易“视而不见”而导致幻觉。Chunk化后只检索最相关的内容喂给LLM
- 一句话
  - 把大象（海量长文本）切成小肉块，让向量检索“好找”，让大模型“好消化”！
### 可能遇到的问题
- Chunk导致语义断裂与上下文丢失
  - 问题表现
    - 一句话或一个完整的逻辑段落被生硬地切成两半，分别存入不同的 Chunk。当检索到后半句时，由于缺少前半句的背景，大模型无法理解。
  - 解决方案
    - **使用递归字符切分：**优先按段落（\n\n）、句子（。 ！ ？）切分，只有当单段字数超标时才进行硬切分，最大程度保留句子完整性。
    - **设置重叠区间 (Overlap)：**在固定长度切片时，设置 10%~20% 的重叠字数（例如 Chunk 大小 512，重叠 50~100 个字符），确保边界信息在前后两个块中都有保留。
    - **引入“邻居扩展”机制：**在检索阶段，动态把召回 Chunk 的物理前后块（Context）一起捞出来喂给大模型。
- **结构破坏**
  - 问题表现
    - 文档中的表格 (Table)、代码块 (Code Block) 或列表 (List) 被切碎。例如表格的表头在 Chunk A，数据行在 Chunk B，导致表格完全失去检索价值。
  - 解决方案
    - ​
      - **布局感知解析：**使用专业的解析工具（如 Unstructured、Marker、PyMuPDF）先将 PDF/Markdown 中的表格提取为独立的 HTML 或 Markdown 文本，并将其作为一个整体强制划分为一个 Chunk。
    - **结构感知切片：**根据 Markdown 的标题级别（#, ##）进行切块，确保一个标题下的内容尽量聚合在一起。
- **指代不明与主语缺失**
  - 问题表现
    - 文章开头写了“关于华为 Mate 60 手机的配置”，后面几个段落一直在用“该手机”、“它”、“这款产品”指代。切片后，后面的 Chunk 失去了“华为 Mate 60”这个核心主语，导致向量检索时无法被命中。
  - 解决方案
    - **元数据注入：**在切片时，将文档的标题（Title）、章节名（Section）、关键字自动作为元数据（Metadata）拼接到每个 Chunk 的头部，或者写入向量数据库的元数据字段中。
    - **大模型主语重写：**在预处理阶段，利用轻量级大模型（或提示词）对每个 Chunk 进行加工，例如：“请为以下文本补全省略的主语或添加 3 个核心关键词”，将重写后的文本用于向量生成。
- 块大小（Chunk Size）难以平衡
  - 问题表现
    - Chunk 设得太大（如 2000 个字符），内容太杂，向量特征被稀释，检索不精准，且浪费大模型 Token；Chunk 设得太小（如 100 个字符），虽然检索精准，但信息量太少，大模型回答时缺乏深度。
  - 解决方案
    - **父子块架构：**业界推荐的高级方案。先切大块，再将大块切分为多个子块；检索时用子块去匹配用户问题，匹配成功后，实际丢给大模型处理的是它对应的父块。平衡了“检索精度”与“生成上下文”。
- 特殊文本处理失败
  - 问题表现
    - 不同语言的切分规则不同。例如：按字符切分时，英文单词（如 "Transformer"）可能被截断成 "Trans" 和 "former"；或者版本号 "v3.14" 中的句号被误当成句尾强行切断。
    - 解决方案
      - **基于 Token 计数切分（而非纯字符数）：**在切分前，调用大模型配套的 Tokenizer（分词器）将文本转化为 Token ID 数组，再按照 Token 数量来截断。
      - **正则保护规则：**很多通用的切片器（如 LangChain 的 SentenceSplitter）会使用正则表达式匹配 [。！？.!?] 来找句子的结尾。它们可能无法很好的处理 数字与版本号灾难 & 英文缩写（i.e.）。需要添加高级正则，例如基于负向先行断言：optimized_regex = r'。|(?<!\d)\.(?!\d)(?<!e\.g)(?<!i\.e)'
      - **代码块与公式：**代码（如 Python、JSON）或数学公式（如 LaTeX $$ ... $$）有严格的闭合语法。对于这类高度结构化的特殊文本，不再使用普通的字符或 Token 切分，而是引入语法感知，使用 AST（语法树）或 Markdown 专用切分器
