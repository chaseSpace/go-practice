# 后端工程师转 AI Agent 岗位学习手册

> 本手册根据 [AI Agent 岗位 JD 汇总](./job_jd.md) 提炼，面向已有 Go、Java、Python 等后端经验，希望转向 Agent 开发、Agent 平台或 Agent 架构岗位的工程师。
>
> JD 样本有限，文中的薪酬和技术名词只用于观察岗位倾向，不代表完整市场统计。

## 一、先看结论：转型不是从零开始

后端工程师转 Agent 岗位，不是把原有技术栈推倒重来，而是在已有工程能力上补齐四层能力：

1. **模型层**：理解 LLM 能做什么、不能做什么，掌握 Prompt、结构化输出、Tool Calling 和模型路由。
2. **Agent 运行时层**：掌握 Agent Loop、状态机、上下文、记忆、工具编排、错误恢复和多 Agent 协作。
3. **知识与评测层**：掌握 RAG、数据摄取、检索与重排、来源验证，以及评估集和回归测试。
4. **生产治理层**：把 Agent 做成高可用、低延迟、可观测、可审计、成本可控的服务。

传统后端能力并没有过时。接口设计、异步任务、数据库、缓存、消息队列、容器化、CI/CD、监控、安全和故障处理，仍然决定一个 Agent 能否进入生产环境。

真正需要完成的认知转换是：

```text
确定性程序：输入 -> 固定逻辑 -> 可预期输出
Agent 系统：输入 -> 概率模型 -> 工具与外部状态 -> 受约束的输出

工程目标：不是消灭不确定性，而是识别、约束、评估和兜底不确定性。
```

## 二、JD 样本总结

### 2.1 岗位真正需要什么

四份 JD 的共同要求可以压缩为以下能力矩阵：

| 能力域 | 基础要求 | 进阶要求 | 生产级证明 |
| --- | --- | --- | --- |
| 后端工程 | Python、API、异步编程、数据库 | 服务拆分、任务队列、缓存、性能优化 | 高可用部署、限流、熔断、重试、CI/CD |
| LLM 基础 | Prompt、Token、上下文窗口、模型 API | 结构化输出、Tool Calling、模型能力边界 | 多模型路由、缓存、降级、成本控制 |
| Agent | ReAct、Agent Loop、工具调用 | 图/状态机编排、记忆、人工介入、多 Agent | 可恢复执行、幂等、超时、循环检测 |
| RAG | Embedding、向量检索 | 混合检索、重排、查询改写、来源验证 | 数据摄取流水线、增量更新、权限过滤 |
| 质量保障 | 单元测试、基本日志 | 离线评测集、轨迹分析、回归测试 | 质量门禁、灰度、Prompt/Schema 版本管理 |
| 平台治理 | Docker、配置管理 | Agent/Tool/Skill/MCP 资产化 | Registry、审批、审计、租户与权限治理 |
| 产品能力 | 理解需求、定义输入输出 | 判断是否应该使用 Agent | 用业务指标证明价值，控制能力边界 |

### 2.2 不同岗位的侧重点

| 岗位 | 核心目标 | 最重要的能力证明 |
| --- | --- | --- |
| Agent 开发工程师 | 实现具体 Agent 产品与服务 | Agent Loop、RAG、工具调用、Python 工程化 |
| 高级 Agent 开发 | 解决复杂流程和生产稳定性 | 高级检索、记忆、数据流水线、评测与部署 |
| Agent 技术经理 | 建平台并推动业务落地 | 架构、业务抽象、内部系统集成、团队与治理 |
| Agent 架构师 | 建立可泛化的运行时与确定性闭环 | 状态机、多 Agent、结构化约束、路由、评测体系 |

建议先以 **Agent 开发工程师** 为转型目标，再根据经历向平台或架构方向发展。直接冲刺架构岗位，需要用真实项目证明你处理过复杂状态、模型失败和线上治理，而不只是读过框架源码。

### 2.3 JD 中反复出现的招聘信号

- **Python 是主栈**：即使原本使用 Go 或 Java，也应能写出类型清晰、可测试、异步安全的生产级 Python。
- **框架只是工具**：会 LangGraph、PydanticAI、AutoGen、CrewAI、LlamaIndex 中的一种还不够，要理解状态、调度、持久化和失败恢复。
- **结构化输出是必修项**：JSON Schema、Function Calling、校验、修复和兜底是从 Demo 到系统的分界线。
- **评测是核心工程能力**：没有评估集和回归测试，就无法证明 Prompt、模型或检索改动是否变好。
- **GitHub 是能力证据**：样本 JD 多次明确要求 GitHub 主页或框架贡献，作品要能运行、能测试、能解释。
- **AI 编程工具是效率要求**：应会用编码 Agent 提升速度，但必须能审查、调试并对生成代码负责。
- **产品判断力不可缺少**：Agent 不是任何业务的默认答案；确定性流程优先用普通代码，模型只处理确实需要语义理解和开放推理的部分。

## 三、后端经验如何迁移

### 3.1 可以直接复用的能力

| 后端经验 | 在 Agent 系统中的对应价值 |
| --- | --- |
| REST/RPC API | 模型网关、Agent 服务、Tool/MCP 接口 |
| 状态机、工作流 | Agent 图编排、任务生命周期、人工审批 |
| 数据库与事务 | Checkpoint、长期记忆、执行记录、幂等 |
| Redis、消息队列 | 缓存、异步任务、事件驱动、长任务恢复 |
| 微服务治理 | 限流、熔断、重试、降级、租户隔离 |
| 日志、指标、Trace | Prompt、模型、工具和检索链路可观测性 |
| Docker/Kubernetes | Agent 服务、模型网关和 Worker 部署 |
| 权限与安全 | Tool 最小权限、知识库 ACL、审批与审计 |
| 单测与集成测试 | Tool 确定性测试、轨迹回放、评测回归 |

### 3.2 必须补齐的能力

- Python 类型系统、`asyncio`、Pydantic、FastAPI、pytest 和常用数据处理工具。
- LLM 推理特征：概率性、上下文限制、幻觉、指令冲突和模型差异。
- Embedding、向量索引、Chunking、混合检索、Rerank 和引用验证。
- Agent 状态设计、Tool Contract、Checkpoint、人工介入和失败恢复。
- 基于样本的质量评测，而不是只看“这次回答感觉不错”。
- Prompt、模型、Schema、数据集和知识库版本的联合管理。

### 3.3 最容易踩的坑

1. **沉迷框架 API**：框架升级很快，先理解原生 Tool Calling 和状态机，再选择框架。
2. **把 Multi-Agent 当高级架构**：可以用一个确定性节点解决的问题，不要拆成多个 Agent。
3. **只做聊天界面**：招聘方更关心执行轨迹、异常处理、评测数据和部署设计。
4. **把向量数据库等同于 RAG**：召回之后还有过滤、重排、上下文组装、引用和答案验证。
5. **用无限重试掩盖错误**：重试必须有错误分类、退避、次数上限和幂等保证。
6. **只测代码，不测语义**：接口返回 200 不代表答案正确，也不代表业务动作安全。
7. **让模型直接执行高风险操作**：写数据库、发消息、付款等动作应增加权限、确认、审计和补偿机制。

## 四、目标能力模型

学习完成后，至少应能独立完成下面这条生产链路：

```text
用户请求
  -> 鉴权与配额
  -> 意图识别/任务分类
  -> Agent 状态机
       -> 模型选择
       -> 知识检索
       -> 工具调用
       -> 输出校验
       -> 重试/降级/人工确认
  -> 结果与引用
  -> Trace、指标、成本、反馈
  -> 离线评测与持续回归
```

不要用“学过”作为完成标准。建议使用四级熟练度：

| 等级 | 判断标准 |
| --- | --- |
| L1 了解 | 能解释概念，能运行官方示例 |
| L2 会用 | 能独立实现小功能并写测试 |
| L3 工程化 | 能处理异常、部署、观测、成本和安全 |
| L4 可设计 | 能比较方案、解释取舍并沉淀复用组件 |

求职 Agent 开发岗位时，核心能力至少达到 L3；架构、评测与平台能力可处于 L2，并有一个方向达到 L3 或 L4。

## 五、16 周学习路线

建议投入每周 10～15 小时，始终坚持“30% 学习，70% 编码和验证”。如果已经熟悉 Python，可以压缩前两周；如果没有后端经验，不建议照此进度执行。

### 第 0 阶段：定位与基线（第 1 周）

**学习内容**

- 阅读目标岗位 JD，按能力域为自己打分。
- 理解 LLM、Agent、Workflow、RAG、Tool、Skill、Plugin、MCP 的边界。
- 理解概率系统与传统后端的质量保障差异。
- 确定一个熟悉的业务领域作为贯穿项目，避免把精力浪费在陌生业务上。

**交付物**

- 一页个人能力雷达图。
- 一份目标岗位要求与个人差距表。
- 一个公开 GitHub 仓库，包含路线图和周进度记录。

**验收标准**

- 能用自己的话解释：Agent 与普通 Workflow 有什么差别，什么时候不该使用 Agent。
- 能画出一个 Agent 请求从入口到模型、工具、数据库和监控系统的完整链路。

### 第 1 阶段：Python 与模型 API（第 2～3 周）

**学习内容**

- Python：类型标注、数据类、Pydantic、异常、迭代器、上下文管理器。
- 并发：`asyncio`、超时、取消、并发限制和异步 HTTP 客户端。
- Web：FastAPI、依赖注入、中间件、流式响应、OpenAPI。
- 模型 API：消息角色、Token、Temperature、上下文窗口、流式输出。
- 结构化输出：JSON Schema、Pydantic 校验、Tool Calling。

**练习项目：模型网关 Lite**

- 封装统一的 `LLMClient` 接口，至少支持两种模型配置。
- 实现超时、指数退避、并发限制和错误分类。
- 记录模型、Token、耗时、调用结果和 Trace ID。
- 用 Pydantic 定义结构化输出，注入格式错误并验证修复或降级。
- 使用 Mock/Fake Model 编写离线测试，CI 中不得依赖真实模型密钥。

**验收标准**

- 并发请求不会阻塞整个服务，取消请求能够向下传播。
- 业务代码不直接依赖某一家模型 SDK。
- 能区分可重试错误、不可重试错误和内容质量错误。
- 配置和密钥不进入代码库，日志不泄露敏感 Prompt 或用户数据。

### 第 2 阶段：从零实现 Agent Loop（第 4～5 周）

**学习内容**

- ReAct、Plan-and-Execute 与确定性 Workflow。
- Tool Schema、工具选择、参数验证和结果序列化。
- Stop Condition、最大步数、Token 预算、时间预算和循环检测。
- 会话状态、Checkpoint、幂等键和执行恢复。
- 人工介入：暂停、批准、拒绝和恢复。

**练习项目：无框架工具型 Agent**

先不用 Agent 框架，自己实现最小运行时：

```python
async def run_agent(state: AgentState) -> AgentResult:
    while not state.finished:
        enforce_budget(state)
        decision = await model.decide(state)

        if decision.kind == "final":
            return validate_final(decision)

        tool = registry.get(decision.tool_name)
        args = tool.input_schema.validate(decision.arguments)
        observation = await execute_with_policy(tool, args)
        state = state.append(decision, observation)

    raise AgentBudgetExceeded()
```

至少实现三个工具：一个只读查询工具、一个计算工具、一个需要人工确认的写操作工具。

**验收标准**

- 同一请求重复提交不会重复执行有副作用的工具。
- 工具不存在、参数错误、超时、返回空值和服务不可用都有明确处理。
- Agent 不会无限循环；达到步数、时间或成本上限会安全退出。
- 进程重启后能从最近 Checkpoint 恢复。
- 每一步的模型输入、决策、工具结果和状态变化均可追踪。

### 第 3 阶段：RAG 与知识流水线（第 6～8 周）

**学习内容**

- Embedding、相似度、向量索引和向量数据库基本原理。
- 文档解析、清洗、Chunking、元数据、去重、增量更新。
- 关键词检索、向量检索、混合检索、查询改写和 Metadata Filter。
- Cross-Encoder/LLM Rerank、上下文压缩、引用和来源验证。
- 多租户知识隔离、文档权限和敏感信息处理。
- Recall@K、MRR、NDCG、答案忠实度与引用正确率。

**练习项目：有依据的企业知识助手**

- 建立可重复执行的摄取流水线，记录文档、版本、Chunk 和索引关系。
- 同时实现关键词检索与向量检索，并做融合排序。
- 回答必须包含可定位到原文的引用；证据不足时明确拒答。
- 构建至少 50 条问题的评估集，包含简单问题、跨段问题、无答案问题和权限问题。
- 对 Chunk 大小、Top-K、检索策略和 Rerank 进行对照实验。

**验收标准**

- 文档修改后可以增量更新，不需要每次重建整个知识库。
- 检索与生成指标分开统计，能判断错误来自召回还是回答阶段。
- 越权文档在检索阶段就被过滤，而不是生成后再隐藏。
- 对每个实验保留配置、数据集版本、结果和结论。

### 第 4 阶段：状态机、多 Agent 与协议化工具（第 9～11 周）

**学习内容**

- 使用 LangGraph 或同类框架表达节点、边、状态、分支、循环和中断。
- Planner、Executor、Reviewer 模式及其适用边界。
- 多 Agent 的上下文隔离、任务分派、结果汇总和失败传播。
- MCP 的 Client、Server、Tool、Resource、Prompt 等核心概念。
- Skill、Plugin、Tool 与 MCP Server 的资产边界和版本策略。

**练习项目：可恢复的任务执行 Agent**

建议选择“工单处理”“代码库问答与变更建议”或“数据分析请求”之一：

- 使用图或状态机显式定义流程，不把流程藏在一个超长 Prompt 中。
- 将确定性校验写成普通代码节点，仅在需要语义判断时调用模型。
- 引入 Reviewer，但只审查有明确规则和风险的关键结果。
- 把至少两个工具封装为 MCP Server，并提供健康检查和契约测试。
- 对高风险动作增加人工批准节点。

**是否需要 Multi-Agent 的判断顺序**

1. 普通函数或规则能否完成？
2. 单次模型调用加结构化输出能否完成？
3. 单 Agent 加多个工具能否完成？
4. 确实存在上下文隔离、职责分工或并行需求时，才使用 Multi-Agent。

**验收标准**

- 流程图能直接对应代码中的状态和跳转。
- 任一节点失败后可以重试、跳过、补偿或转人工，而不是整条任务报废。
- Agent 之间不共享无边界的完整上下文。
- Tool/MCP 接口有版本、Schema、超时、权限和错误语义。
- 能用数据说明多 Agent 相比单 Agent 是否提升质量，以及增加了多少成本和延迟。

### 第 5 阶段：评测、可观测与安全（第 12～14 周）

**学习内容**

- 离线评测：Golden Dataset、规则评分、模型裁判、人工抽检。
- 在线评测：成功率、任务完成率、用户反馈、人工接管率。
- Agent 轨迹评估：工具选择、参数正确率、步骤数、循环和终止原因。
- 可观测性：Trace、结构化日志、指标、Token 与成本归因。
- 安全：Prompt Injection、越权调用、数据泄露、危险输出和供应链风险。
- 发布：Prompt、模型、Tool Schema、知识库和评估集版本化，灰度与回滚。

**评测集应包含的样本**

- 正常主流程。
- 模糊问题和信息不足问题。
- 对抗指令、越权请求和提示注入。
- 工具超时、返回脏数据、部分成功和重复执行。
- 超长上下文、无相关文档和相互冲突的证据。
- 模型拒答、格式错误和错误选择工具。

**核心指标**

| 层级 | 建议指标 |
| --- | --- |
| 模型 | 格式通过率、拒答准确率、Token、首 Token/总延迟 |
| 检索 | Recall@K、MRR/NDCG、权限过滤正确率、引用命中率 |
| 工具 | 选择正确率、参数正确率、成功率、P95 延迟、重试率 |
| Agent | 任务完成率、平均步骤数、循环率、人工接管率、单任务成本 |
| 业务 | 处理时长、一次解决率、错误操作率、用户采纳率 |

**验收标准**

- 每次修改 Prompt、模型、检索策略或 Tool Schema 都能跑自动回归。
- CI 中存在质量门禁，核心指标退化时不能直接发布。
- 能通过 Trace 还原一次失败请求，而不是依赖复现时的运气。
- 日志、评测样本和模型输入均执行脱敏与访问控制。
- 对模型裁判进行人工校准，不能把它当绝对真值。

### 第 6 阶段：生产化与作品集（第 15～16 周）

**学习内容**

- Docker 镜像、配置、迁移、健康检查和优雅退出。
- API 与 Worker 分离，队列化长任务，背压和并发控制。
- 限流、熔断、缓存、超时预算、降级和模型故障转移。
- 多模型路由：按质量、成本、延迟、上下文和合规要求选择模型。
- Agent、Tool、Skill、Prompt 的 Registry 与审批、审计、发布流程。

**最终交付物**

- 一条命令可启动的完整项目。
- 架构图、时序图、状态机图和关键设计决策记录。
- 公开 Demo 或演示视频。
- 自动测试、评测报告、压测报告和成本分析。
- 故障演练记录：模型超时、向量库不可用、工具部分失败、任务恢复。
- 一篇复盘文章：问题、取舍、失败、数据和下一步，而不是功能宣传。

**验收标准**

- 新环境可按 README 在 15 分钟内启动核心流程。
- 没有模型密钥时仍可用 Fake Model 完成测试。
- 能回答系统在超时、重复请求、进程崩溃和依赖故障时会怎样。
- 能展示一次改动前后的离线评测数据，而不是只演示最佳案例。

## 六、贯穿全程的毕业项目

推荐做一个“企业工单处理 Agent”。它能同时覆盖 JD 中的 RAG、工具调用、状态机、人工介入、评测和治理要求。

### 6.1 业务流程

```text
接收工单
  -> 分类与风险判断
  -> 检索知识库和历史工单
  -> 制订处理计划
  -> 调用只读工具收集环境信息
  -> 生成建议
  -> 规则校验/Reviewer 审查
  -> 低风险自动回复 | 高风险人工批准
  -> 更新工单系统
  -> 收集结果并进入评测集
```

### 6.2 建议架构

```text
API Gateway
  ├── Auth / Rate Limit / Tenant
  └── Agent API
        ├── Orchestrator / State Machine
        ├── Model Gateway
        ├── Retrieval Service
        ├── Tool / MCP Registry
        ├── Policy & Guardrail
        └── Checkpoint Store

Worker / Queue
  ├── Document Ingestion
  ├── Long-running Tasks
  └── Offline Evaluation

Observability
  ├── Trace
  ├── Metrics / Logs
  └── Cost & Quality Dashboard
```

### 6.4 关键设计原则

- **模型负责判断，代码负责约束**：金额、权限、状态转换等硬规则必须由代码校验。
- **副作用延后**：先生成计划并校验，再执行写操作；高风险操作必须人工确认。
- **状态显式化**：重要状态进入持久化 State，不依赖模型“记住”。
- **上下文最小化**：只向模型提供当前决策需要的信息，降低成本与泄露风险。
- **失败可分类**：区分模型、解析、检索、工具、业务和基础设施错误。
- **一切可版本化**：Prompt、Schema、模型、检索配置、工具和数据集必须能追溯。
- **一切改动可评估**：先记录基线，再比较质量、延迟与成本。

## 七、框架选择建议

不要同时学习所有框架。建议采用“一主两辅”：

- **主框架：LangGraph 或同类图编排框架**。用于掌握状态、节点、分支、循环、持久化与人工介入。
- **数据方向辅助：LlamaIndex 或框架无关的检索组件**。用于学习知识摄取、索引与检索。
- **类型与测试辅助：PydanticAI 或原生 Pydantic + 模型 SDK**。用于学习结构化输出和可测试性。

如果原技术栈是 Go，可以用 Go 编写高并发 Tool、MCP Server、网关或基础设施服务，但建议用 Python 完成至少一个完整 Agent 项目，以满足岗位对 Python 生态的要求。

选择框架时重点比较：

1. 状态是否显式、可持久化、可迁移。
2. 节点是否容易单测，是否能注入 Fake Model 和 Fake Tool。
3. 是否支持暂停、恢复、流式输出和人工介入。
4. 失败语义、重试和幂等是否能由业务控制。
5. Trace 是否完整，能否导出或接入现有观测系统。
6. 是否锁定模型供应商，升级和迁移成本多高。

## 八、工程检查清单

### 8.1 模型调用

- [ ] 请求有总超时，每一步有子超时。
- [ ] 有模型抽象层，不在业务中散落供应商 SDK。
- [ ] 结构化输出经过 Schema 校验。
- [ ] 有格式修复、模型降级或人工兜底策略。
- [ ] 记录 Token、延迟、模型版本、缓存命中与成本。
- [ ] 敏感数据在发送前经过分类、脱敏和授权检查。

### 8.2 Tool 与 MCP

- [ ] 工具名称和描述清晰，不存在大范围语义重叠。
- [ ] 输入、输出和错误均有稳定 Schema。
- [ ] 权限遵循最小化原则，读写工具分离。
- [ ] 写操作支持幂等、确认、审计和必要的补偿。
- [ ] 外部依赖具有超时、重试、限流和熔断策略。
- [ ] 工具结果大小受限，不把超大原始结果直接塞回上下文。

### 8.3 Agent 运行时

- [ ] 有最大步数、时间、Token 和费用预算。
- [ ] 有重复动作或循环检测。
- [ ] 状态可持久化，任务可暂停和恢复。
- [ ] 节点失败有明确的重试、降级、转人工或终止路径。
- [ ] 对副作用操作保存审批者、参数、时间和结果。
- [ ] 并发执行不会破坏状态一致性。

### 8.4 RAG

- [ ] 文档来源、版本、权限和更新时间可追溯。
- [ ] 摄取流程可增量、可重跑、可去重。
- [ ] 检索评测与回答评测相互独立。
- [ ] 召回结果经过权限过滤和必要的重排。
- [ ] 回答包含引用，证据不足时可以拒答。
- [ ] 删除文档后，索引、缓存和派生数据能同步清理。

### 8.5 评测与发布

- [ ] 评估集覆盖主流程、边界、故障和对抗样本。
- [ ] 数据集、Prompt、模型、Schema 和检索配置均有版本。
- [ ] 有确定性断言，也有经过校准的语义评分。
- [ ] 回归报告同时展示质量、延迟和成本。
- [ ] 发布支持灰度、对照实验与快速回滚。
- [ ] 线上失败样本经脱敏和审核后进入评估集。

## 十、作品集与 GitHub 建设

一个有说服力的 Agent 仓库至少应包含：

- 清晰的问题定义、非目标和业务边界。
- 架构图、状态机图和关键决策记录。
- 可重复的启动命令、示例数据和 Demo。
- Fake Model/Fake Tool、单测、集成测试和评测命令。
- 至少一份包含基线的评测报告。
- 异常、权限、成本、数据安全和故障恢复说明。
- 真实的提交历史，能看到从简单实现到工程化的演进。

建议形成三个递进作品：

1. **无框架 Agent Runtime**：证明理解 Agent Loop 和工具调用底层机制。
2. **Agentic RAG 服务**：证明检索、数据流水线、来源验证和评测能力。
3. **生产级业务 Agent**：证明状态机、MCP、治理、可观测、部署和产品判断力。

如果有余力，可以给主流框架贡献文档、测试、Bug 修复或小型功能。高质量 Issue 复现和 Pull Request 往往比再做一个套壳聊天机器人更能体现源码阅读与协作能力。

## 十一、简历写法

不要写：

> 熟悉 LangChain、LangGraph、RAG、向量数据库和 Prompt Engineering。

推荐写成：

> 基于显式状态机实现 8 节点工单 Agent，支持 Checkpoint、人工审批、幂等工具调用和失败恢复；构建 120 条回归集，将任务完成率从 71% 提升至 86%，P95 延迟降低 24%，单任务模型成本降低 31%。

项目描述采用以下公式：

```text
业务问题 + 你的职责 + 关键设计 + 失败治理 + 量化结果
```

没有线上流量时也不要编造指标。可以诚实使用：

- 离线评估集规模与结果。
- 故障注入通过率。
- 并发压测的吞吐和 P95/P99。
- Token、成本和延迟的对照实验。
- 人工盲测或专家标注的一致性。

## 十二、面试准备

### 12.1 必须能讲清的系统设计题

- 设计一个可恢复的长任务 Agent，进程重启后如何继续？
- Agent 重复调用付款或写库工具，如何保证安全与幂等？
- 如何判断 RAG 错误来自检索还是生成？
- 如何为 Prompt 或模型升级建立回归测试与质量门禁？
- 如何设计质量、成本、延迟之间的模型路由？
- 单 Agent 何时应该拆成 Multi-Agent？拆分后如何控制上下文和故障？
- MCP Server 如何做鉴权、租户隔离、Schema 版本和审计？
- 如何防御 Prompt Injection 导致的越权工具调用？
- 如何让 Reviewer 真正提高可靠性，而不是增加一次同源幻觉？

### 12.2 回答框架

回答 Agent 系统设计题时，建议按以下顺序展开：

1. 明确业务目标、风险等级和成功指标。
2. 区分确定性逻辑与需要模型判断的部分。
3. 定义状态、节点、工具契约和终止条件。
4. 说明超时、重试、幂等、恢复、降级和人工介入。
5. 说明权限、隐私、审计和提示注入防护。
6. 说明离线评测、在线指标、Trace 和发布策略。
7. 最后讨论成本、延迟、扩展性与方案取舍。

### 12.3 高频基础问题

- Temperature 与 Top-P 的作用是什么？为什么生产场景仍无法保证完全确定？
- Function Calling 与普通 JSON 输出有什么差别？Schema 失败如何处理？
- Chunk 大小、Overlap 和 Top-K 如何影响召回与成本？
- 向量检索、关键词检索和混合检索分别适用于什么数据？
- Checkpoint 与 Memory 有什么区别？
- 模型超时为什么不能简单无限重试？
- 为什么模型裁判需要校准？如何避免位置偏差和自我偏好？
- Agent Trace 应记录哪些字段，又有哪些数据不应该记录？
