## 人工笔记 —— Agent 原理/架构/工程实践

### 关键词

控制流、上下文工程、工具设计、记忆、多 Agent 组织、评测、追踪和安全等。

### 0. Agent 原理

感知（输入）—— 决策（思考）—— 行动（执行） —— 反馈（再输入）

### 1. Agent Loop 的基本运转方式

Agent Loop 的核心实现逻辑抽象后其实不到 20 行代码：

```js
const messages: MessageParam[] = [{role: "user", content: userInput}];

while (true) {
    const response = await client.messages.create({
        model: "claude-opus-4-6",
        max_tokens: 8096,
        tools: toolDefinitions,
        messages,
    });

    if (response.stop_reason === "tool_use") {
        const toolResults = await Promise.all(
            response.content
                .filter((b) => b.type === "tool_use")
                .map(async (b) => ({
                    type: "tool_result" as const,
                    tool_use_id: b.id,
                    content: await executeTool(b.name, b.input),
                }))
        );
        messages.push({role: "assistant", content: response.content});
        messages.push({role: "user", content: toolResults});
    } else {
        return response.content.find((b) => b.type === "text")?.text ?? "";
    }
}
```

看过不少 Agent 实现和官方 SDK ，结构都差不多，循环本身相当稳定，从最小实现一路扩展到支持子 Agent 、上下文压缩和 Skills
加载，主循环基本没有变化，新增能力通常都是叠加在循环外部，而不是改动循环内部。

新能力基本只通过三种方式接入：扩展工具集和 handler
、调整系统提示结构、把状态外化到文件或数据库，不应该让循环体本身变成一个巨大的状态机，模型负责推理，外部系统负责状态和边界，一旦这个分工确定下来，核心循环逻辑就很少需要频繁调整了。

#### 1.1 Workflow 和 Agent 有什么区别

Anthropic 对这两类系统有一个直接区分：执行路径由代码预先写死的是Workflow，由LLM动态决定下一步的是Agent，核心区别在于控制权掌握在谁手里。

| 维度    | Workflow        | Agent              |
|:------|:----------------|:-------------------|
| 控制权   | 代码预定义，同输入必走同一路径 | LLM 动态决策，可能需要评测验证  |
| 执行方式  | 工具顺序固定，错误走预设分支  | 工具按需选择，模型可尝试自我修复   |
| 状态与记忆 | 显式状态机，节点跳转清晰    | 隐式上下文，状态在对话历史中累积   |
| 维护成本  | 改流程需修改代码并重新部署   | 调整系统提示即可，无需重新部署    |
| 可观测性  | 日志定位节点，延迟可预估    | 需完整执行记录理解决策链，轮数不固定 |
| 人机协作  | 人在预设节点介入        | 人在任意轮次介入或接管        |
| 适用场景  | 流程固定、输入边界清晰     | 需要中间推理与灵活判断        |

#### 1.2 五种常见控制模式

大多数AI系统拆开看，其实都是这五种模式的组合。很多场景并不需要完整的Agent自主权，把其中几种模式搭起来就够了，关键还是看任务本身适合哪一种设计。

1. 提示链：任务拆成顺序步骤，很像工厂流水线，每个工位只负责一件事。示例任务：写分析报告（搜集信息 → 整理大纲 → 写正文 → 润色 →
   翻译英文）
2. 路由：先分诊，再找专家。示例任务：客服系统（识别语义 -> 引用对应的知识库回答）
3. 并行：几个人同时干，目的是提高速度或降低单个AI错误率。示例任务：做新能源汽车分析（同时分析不同品牌以及市场政策等，最后合并）；示例任务2：分析这份合同有没有风险？（同时让
   5 个 AI 独立判断，采用多数意见）
4. 编排器——工作者：项目经理带团队，“经理”负责拆分任务并调用 worker 完成任务。示例任务：研究某个市场（由一个较为聪明的LLM负责拆分任务，并交给其他普通LLM完成，最后整理结果）
5. 评估器-优化器：写完有人挑刺，再返工。示例任务：帮我写一条很牛的广告文案。（Evaluator先给第一个版本，Optimizer发表意见，让前者返工直到后者满意）

#### 1.3 超时控制与失败边界

超时控制的核心是给任务建立不可无限重置的时间预算。通常需要三层：

```text
任务总超时
├── 单步骤 / 单 Agent 超时
│   ├── 单次模型调用超时
│   └── 单次工具或外部服务调用超时
```

- **任务总超时**限制整个任务，耗尽后不再启动新步骤，并取消正在执行的工作。
- **单步骤超时**防止某个 Agent 或阶段独占全部预算。
- **外部调用超时**限制单次模型、HTTP、数据库或命令调用。

局部预算必须从父任务派生：

```text
实际截止时间 = min（父任务截止时间，当前步骤截止时间）
```

同时设置时间和次数边界：总耗时、步骤耗时、单次调用耗时，以及最大推理轮数、工具调用数、重试次数和子任务数。重试不能重置总预算；只有临时故障、剩余时间充足且操作幂等时才有限重试。认证、权限、参数错误和不可幂等的副作用操作不应直接重试。

不同控制模式需要不同失败策略：

| 控制模式    | 单个步骤失败后的推荐行为               |
|:--------|:---------------------------|
| 提示链     | 必需步骤失败则停止；非必需步骤可降级         |
| 路由      | 进入保守 fallback，或切换经过授权的备用专家 |
| 并行      | 其他分支继续，最后按必需分支或最低成功数判断     |
| 编排器—工作者 | 记录子任务状态，选择重试、重新分配或放弃非关键任务  |
| 评估器—优化器 | 达到时间或轮数上限后，返回最佳版本并标记是否达标   |

取消是协作式的：上层只能发出取消信号，模型、工具、网络请求和子任务必须主动响应、停止新工作并释放资源。忽略取消的执行单元仍会在后台占用资源。

结果不能用空字符串伪装成功，至少区分 `success`、`partial`、`failed`、`timeout` 和 `cancelled`
。运行轨迹记录开始时间、截止时间、耗时、重试次数与终止原因，但不要记录密钥和未脱敏的输入输出。

### 2. 为什么 Harness 比模型更关键

Harness 是指围绕 Agent 构建的测试、验证与约束基础设施，这里的 Harness 至少包括四个部分：验收基线、执行边界、反馈信号和回退手段。

模型虽然重要，但决定系统能不能稳定运行的，往往是这些外围工程条件。这个判断在代码编写这类高可验证任务上最成立，但在开放式研究、多轮协商这类弱验证任务里，模型上限本身仍然更关键。

#### 2.1 真实案例——OpenAI 的 Agent 优先开发实践

3 个工程师 5 个月写了百万行代码，将近 1500 个 PR ，是传统开发速度的 10 倍。

### 3. 上下文工程为什么决定稳定性

Transformer 的注意力复杂度是 $O(n^2)$，上下文越长，关键信号越容易被噪声稀释，实践里最常见的失效模式是无关内容一旦占到上下文的大头，Agent
的决策质量就会明显下滑，这类现象通常被叫作 Context Rot ，很多看起来像模型能力不足的问题，往往可以追溯到上下文组织不当。

#### 3.1 上下文为何要分层

问题通常不是窗口不够长，而是信息密度不对，偶尔用的东西每次都加载进来，稳定的规则和动态的状态混在一起。模型的注意力会被大量无关内容淹没，而无法聚焦于真正有用的内容。
解决方式是按信息使用频率和稳定性分层管理，每层只放自己的东西：

- 常驻层：身份定义、项目约定、绝对禁止项，每次会话都必须成立的内容。保持短、硬和可执行。
- 按需加载：Skills和领域知识、描述语常驻，但完整内容需要时再读取。
- 运行时注入：当前时间、渠道ID、用户偏好等动态信息，按需读入
- 记忆层：跨会话经验写入 MEMORY.md，也不进入系统提示语，按需读取
- 系统层：Hooks 或代码规则处理确定性逻辑，完全不进上下文。

不要把确定性逻辑放进上下文，凡是可以通过Hooks、代码规则或工具约束表达的内容，都应该交给外部系统处理，不让模型反复读取。

#### 3.2 三种常见压缩策略

| 策略     | 成本 | 丢什么     | 适用场景      |
|:-------|:---|:--------|:----------|
| 滑动窗口   | 极低 | 早期上下文   | 简短对话      |
| LLM 摘要 | 中  | 细节，保留决策 | 长任务、含关键决策 |
| 工具结果替换 | 低  | 工具原始输出  | 工具调用密集型   |

滑动窗口最简单，但会丢掉早期决策背景。LLM摘要的进阶做法是 branch summarization，摘要时保留架构决策、未完成任务和关键约束。
最后一个工具结果替换，意思是 工具返回内容太长时，不要直接把原始结果塞入上下文，而是用短结果（摘要）替换，主要解决日志、搜索结果、代码输出特别长的问题。

#### 3.3 Prompt Caching

Prompt Caching 本质上就是：**AI 发现这次请求前面有一大段内容和上次一模一样，就不再重新“读一遍”，而是直接复用之前算好的结果。
**
所以做 Agent 时，最好把长期不变的内容，比如系统规则、工具说明、固定背景，尽量放在前面；把用户当前问题、时间、搜索结果这类经常变化的内容放后面。
这样前面的内容越稳定，越容易命中缓存，响应就会更快、输入成本也更低。反过来，如果你总在前面改一点东西，哪怕只改了很小一部分，后面的缓存都可能接不上，又得重新算。

#### 3.4 Skills 的作用

Skills 一般用来扩展 Agent 的能力，但不是每次处理都需要用到Skill，所以系统提示词中只会常驻对 Skills
的基本能力简单描述，当LLM决定需要某个Skill再读取对应的 Skill doc。

例如系统提示词里只放一个很短的索引：

```
Available skills:

- deploy
  Use when: 部署、发布、回滚、部署后检查
  Don't use when: 普通代码修改或代码排错
  Output: 部署步骤、执行结果、健康检查、回滚方案

- code-review
  Use when: Review 代码、diff、PR 或检查代码风险
  Don't use when: 单纯编写新代码
  Output: 问题、风险等级、修改建议

- git-workflow
  Use when: Git 分支、commit、merge、rebase、冲突、PR
  Don't use when: 与 Git 无关
  Output: 操作步骤、命令、注意事项

当某个 skill 与当前任务明确匹配时，再加载对应的 SKILL.md，且每次最多只加载1个，不要预先加载所有 skills。
```

> 每个字段的描述控制在10字以内才是高效的。另外，"何时该用我"比"我能做什么"重要得多。

注意，其中的`Use when`等描述是非常必要的，这有助于 AI 明确 Skill 的能力边界。其次，Skills 不能等 Agent想起来在用，要每轮都先扫描
Skills.md，
但扫描成本要很低，加载数量要受控。如果Skill 会触发外部API调用，那么doc里面要补充速率限制，尽量批量写、429主动等待。

##### 3.4.1 Skill数量控制

1. **控制 Skill 数量**：系统提示词里只放高频、常用的 Skill，避免默认列表越来越长。

2. **低频 Skill 按需发现**：不常用的 Skill 可以放到二级目录或 Skill Registry，需要时再检索和加载，不必长期占用上下文。

3. **极低频能力不一定要做 Skill**：如果只是偶尔查资料，没有固定流程、工具调用或执行约束，直接用普通文档通常更合适。

4. **Skill 正文不要写成超长手册**：`SKILL.md` 只保留核心流程和规则，详细说明、示例、参考资料拆到 supporting files。

5. **一个 Skill 尽量只负责一类任务**：不要让一个 Skill 同时覆盖 review、deploy、debug、incident 等多个差异很大的场景，否则容易路由错误。

6. **有副作用的 Skill 必须写清调用边界**：像部署、删除、修改数据这类操作，要明确什么情况下允许执行、什么时候需要确认、什么时候禁止执行。

7. **好的 Skill 应该满足三个特点**：职责单一、触发条件清楚、正文精简；涉及危险操作时，再加明确的安全边界。

##### 3.4.2 Skill 正文实践

1. **Skill 索引描述**：约 **30～100 字**，只说明“什么时候用、什么时候不用、做什么”。

2. **`SKILL.md` 正文**：建议控制在 **500～1500 个中文字符**，大约 **500～1200 tokens**。通常足够写清：

    * 使用场景
    * 不使用场景
    * 执行步骤
    * 工具调用规则
    * 输出要求
    * 风险边界

3. **复杂 Skill**：可以到 **2000～3000 字**，但再长就建议拆分，不要继续往正文堆。

4. **大量示例、API 文档、命令手册**：放到 supporting files，例如：

```text
skills/deploy/
├── SKILL.md          # 800~1500 字
├── examples.md
├── rollback.md
└── kubernetes.md
```

SKILL.md 放“每次执行都必须知道的东西”，supporting files 放“遇到特定情况才需要查的东西”。

5. **判断标准不是字数，而是“执行时是否必须知道”**：模型完成这个 Skill 每次都需要的信息放 `SKILL.md`；只是偶尔需要查的信息放外部文件。

可以简单记成：

> **Skill 正文尽量控制在 1000 字左右，超过 2000～3000 字就应该考虑拆文件。**

尤其不要把 `SKILL.md` 写成几十页操作手册，否则虽然是“按需加载”，一旦加载还是会一次性吃掉大量上下文。

#### 3.5 压缩最容易丢掉什么

上下文压缩最容易出问题的地方，不是摘要得太短，而是把任务继续执行所需要的信息压没了。
压缩时应优先删除能够重新查询或重新生成的内容，例如冗长的工具输出、重复日志和中间结果；
优先保留已经确认的架构决策、用户约束、关键修改、未完成任务、重要测试结果，以及会影响后续判断的失败原因。对于文件名、函数名、PR
编号、commit hash、UUID、URL、IP、端口等后续还需要引用的标识符，应原样保留，不能随意改写。最好在系统规则中明确一套压缩优先级，
让模型知道“什么可以丢，什么绝对不能丢”。

#### 3.6 文件系统很适合做 Agent 的外部上下文

与其把日志、搜索结果、工具返回值和历史记录全部塞进模型，不如把大内容保存成文件，只在上下文里保留文件路径、摘要和关键索引；真正需要某段信息时，再通过
grep、rg 或局部读取把相关部分取回来。这样可以把“全部加载”变成“按需加载”，尤其适合大日志、大型工具结果和长时间运行的任务。
长任务也可以采用类似思路：压缩时保留当前状态和历史文件的位置，需要追查细节时再回到原始记录中检索。关键不是用了文件系统，而是做到“大内容外置、上下文只放索引、需要时局部读取”。

#### 3.7 工具决定 Agent 真正能做什么

##### 3.7.1 好的工具不是简单把现有 API 包一层，而是站在 Agent 的角度设计：模型想完成什么任务，就给它一个语义清楚、粒度合适的操作。例如，相比：

```
get_post
update_title
update_content
save_post
```

很多场景下更适合直接提供：

```update_yuque_post(post_id, title, content_markdown)```

模型少做几次选择，出错机会也更少。

##### 3.7.2 一个好工具通常有几个特点

- 粒度合适：对应一个明确的业务动作，而不是一个底层 API Endpoint。
- 描述清楚：不仅告诉模型“它能干什么”，还告诉模型“什么时候该用、什么时候不要用”。
- 返回精简：只返回下一步判断真正需要的数据。
- 错误可处理：告诉模型为什么失败、能不能重试、下一步应该怎么办。
- 副作用明确：删除、发布、付款、修改数据等操作要清楚标明风险和确认要求。

##### 3.7.3 工具设计正在从“API 思维”变成“Agent 思维”

可以粗略理解成三个阶段：

```
第一阶段：API Wrapper
一个 API Endpoint ≈ 一个工具

第二阶段：Agent-oriented Tool
一个明确任务动作 ≈ 一个工具

第三阶段：Advanced Tool Use
工具可以动态发现、程序化组合，并通过示例帮助模型正确调用
```

第三阶段常见的三个方向：

- Tool Search：不要把几百个工具全部塞给模型，先搜索相关工具，再按需加载。
- Programmatic Tool Calling：让代码负责循环、过滤、聚合等机械操作，中间数据不必每一步都经过 LLM。
- Tool Use Examples：Schema 只能告诉模型“参数长什么样”，示例还能告诉模型“实际应该怎么用”。

##### 3.7.4 为什么工具消息也要隔离

Agent 框架里的消息，不等于都要发给 LLM。 运行过程中会产生很多内部状态，例如压缩事件、通知、重试、缓存命中、trace、工具耗时等，这些信息对框架有用，但对模型推理往往没有价值，直接塞进去只会增加
token 和噪声。更好的做法是让框架保存完整事件流，而在调用模型前做一次过滤，只把用户消息、模型回复、必要的工具结果以及真正影响下一步决策的信息传给
LLM。这样可以做到：框架知道全部，模型只看自己需要知道的部分。

### 4. 记忆系统如何设计

Agent 不具备原生的时间连续性，会话结束后，上下文随之清空。下次启动时也不会自动保留此前状态，要让系统具备跨会话的一致性，记忆层得单独设计，它是Agent的一层基础设施，不是可以事后补上的能力。

#### 4.1 四种记忆

这里不是按存储介质分， 而是按Agent实际要解决的问题来分：

- **上下文窗口**，工作记忆：当前任务所需的最小信息，token有限，得主动管理；
- **Skills**，程序性记忆：做某事的能力，按需加载不常驻
- **JSONL会话历史**，情景记忆：历史会话，磁盘存储，可以跨会话搜索
- **MEMORY.MD**，语义记忆：Agent 主动写入认为重要的事实，每次启动时注入系统提示
- **memory/YYYY-MM-DD.md** 原始记忆：Agent 主动写入的每日工作日志 / 原始记忆。
    - 记录当天发生过什么：用户要求、执行步骤、工具结果、关键结论、失败原因等。
    - 保留原始细节：相比 MEMORY.md 的精选长期记忆，这里可以更完整、更啰嗦。
    - 方便事后检索：以后 Agent 需要回忆某件事时，通过 memory_search 找到相关日期和片段。
    - 帮助恢复任务现场：比如昨天做到哪、试过哪些方案、为什么没成功，可以从日志里重新构建上下文。
    - 作为长期记忆的来源：其中真正长期有价值的事实，可以再提炼进 MEMORY.md。

##### OpenClaw 的记忆方案

OpenClaw 当前是 Vector Search + BM25 Keyword Search 的混合检索。

对于小型Agent，完全可以从md + sqlite FTS5（全文搜索）开始。当确实需要语义搜索时，才需要引入向量搜索，
sqlite可以通过引入插件（sqlite-vec 或 vec1）来支持小规模数据的向量搜索。

sqlite 作为记忆表的使用步骤如下：

```
# 写入
1. 记忆写入 memory 主表
2. trigger 同步主表数据到 虚拟索引表（fts5索引类型）

# 查询
1. 用户问题
2. FTS MATCH
3. BM25 相近度排序（可选）
4. 取 Top 5
5. 塞给LLM
```

##### 4.3 记忆整合

确定了记忆分层方案后，剩下的就是确定归档检查点，也就是记忆归档的时机。一般来说，就是当活跃上下文接近设定的Token预算时，Agent截取
lastConsolidatedIndex
到最新一条会话，并判断是否需要压缩，是就压缩成结构化摘要（memory/YYYY-MM-DD.md），然后更新
lastConsolidatedIndex。要注意，近期（比如最近10条）消息要留在活跃上下文里面，旧消息保存在日志或归档中，需要细节时还能重新检索。
然后进一步从摘要中提炼**长期事实**，更新到 MEMORY.md。如果摘要失败，就保留原始消息等待重试。

```
Messages
   ↓
上下文是否接近预算？
   ↓ yes
选择可整合的旧消息
   ↓
保存/确认原始消息已有归档
   ↓
LLM summarize
   ↓
成功？
 ┌───────┴────────┐
yes              no
 ↓                ↓
保存摘要          保留原始消息
 ↓                ↓
提炼长期事实      不推进 pointer
 ↓
必要时写 MEMORY.md
 ↓
更新 lastConsolidatedIndex
 ↓
从活跃上下文移除旧消息
```

可以记成三个原则：

> 先归档，再压缩；成功才推进指针；长期记忆和对话摘要分开。
