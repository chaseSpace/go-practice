# Plan 1：RAG 概念、背景与本质——让回答有可追溯证据

## 本节只解决什么

建立 RAG 的完整心智模型：它解决什么问题、由哪些步骤组成、为什么检索结果必须能追溯到真实文档，以及它与记忆、搜索、微调的边界。

本节只建立文档证据链，不调用 LLM、不创建向量库、不评估回答质量。完成后，你应能看懂后续 Plan 中每个组件在 RAG 链路里的位置。

## RAG 是什么

RAG 是 **Retrieval-Augmented Generation（检索增强生成）**。它不是让模型“学会”一批新资料，而是在用户提出问题时，从受管语料中找出相关证据，把证据连同问题一起交给模型生成答案。

```text
知识在文档中                    知识在本次模型输入中
源文件 -> 解析 -> 分块 -> 索引 -> 检索证据 -> 问题 + 证据 -> 回答 + 引用
```

例如，用户询问“SQLite 文档里如何创建表”：系统不应只让模型凭训练知识回答，而应先从当前 `learn_rag/data/` 中的 PDF、TXT、DOCX
找出涉及创建表的段落，再让模型依据这些段落回答，并标出文件与页码。

## 为什么需要 RAG

通用 LLM 即使能力很强，也有几个天然限制：

- **知识可能过时**：模型训练结束后不会自动知道新文档或新规则。
- **不知道私有资料**：公司文档、个人笔记、本地 PDF 不在模型参数中。
- **无法证明来源**：即使答案恰好正确，也未必能说明依据哪份材料。
- **上下文有限**：不能把整个知识库一次性塞入 Prompt；成本、延迟和干扰都会快速增长。
- **权限不同**：同一个问题的可用资料取决于租户、用户角色和可见范围。

RAG 将“模型本身会什么”与“本次请求允许使用什么资料”分开。文档可以独立更新、删除、重建索引和施加权限，而不需要重新训练模型。

## RAG 的本质

RAG 的本质不是“向量数据库 + LLM”，而是一个**受约束的证据选择与回答系统**：

```text
给定问题 q 和允许访问的语料 C：

1. 在 C 中取回候选证据 E
2. 让生成器只根据 q + E 作答
3. 将答案中的关键结论关联回 E 的来源
```

其中最关键的不是“取回了多少文本”，而是三个约束：

1. **来源约束**：每段证据都能回到 `DocumentID`、URI，PDF 还能回到页码。
2. **访问约束**：租户、可见性等硬过滤在检索前生效，而不是让模型在生成后“自觉保密”。
3. **事实约束**：证据不足时应拒答、说明资料不足或请求补充，而不是把模型常识伪装成资料结论。

后续的 embedding、SQLite-vec、Milvus、rerank 都是在改善“如何从允许语料中选出 E”；它们不自动保证回答真实。

## 两条必须分开的链路

RAG 总有一条离线的索引链和一条在线的问答链。

```text
离线索引链
TXT / PDF / DOCX
  -> 提取文本
  -> 清洗、分块、补充 metadata
  -> embedding
  -> 写入可检索索引

在线问答链
用户问题 + 身份/租户
  -> query embedding
  -> 权限过滤 + Top-K 检索
  -> 证据去重、预算裁剪、引用标签
  -> 受约束生成
  -> 答案、引用、检索轨迹
```

不要把这两条链混成“用户提问时顺便重建全库”。索引重建通常耗时、可失败、需要版本管理；在线检索应尽量只读稳定索引。

## 技术关键词

| 关键词                   | 含义                                  | 在本系列的位置                              |
|-----------------------|-------------------------------------|--------------------------------------|
| Corpus（语料库）           | 允许进入知识库的一组源文件或记录                    | `learn_rag/data/` 与 `RAG_SOURCE_DIR` |
| SourceDocument        | 从一个源文件提取出的标准文档                      | Plan 2                               |
| Metadata              | 格式、来源、租户、可见性、页码、版本等非正文信息            | Plan 2、5                             |
| Chunk                 | 文档被切成的可检索最小文本单元                     | Plan 3                               |
| Embedding             | 将文本映射为固定维度数值向量的模型                   | Plan 4                               |
| Vector                | embedding 的数值结果；本身没有来源和权限语义         | Plan 4                               |
| Similarity / Distance | 衡量 query 与 chunk 接近程度的数值            | Plan 4、5、8                           |
| Retriever             | 根据 query、过滤条件和 Top-K 返回候选 chunk 的组件 | Plan 5                               |
| Top-K                 | 最多保留的候选数量；不是正确性的保证                  | Plan 5                               |
| Filter                | 在检索时施加的租户、可见性、格式等硬约束                | Plan 5、11、12                         |
| Context               | 实际放入模型 Prompt 的有限证据文本               | Plan 6                               |
| Grounding             | 让回答只依据输入证据，并能说明引用来源                 | Plan 6、7                             |
| Citation              | 从答案回到 URI、页码、chunk 的引用信息            | Plan 6                               |
| Recall@K / MRR        | 衡量正确证据是否被召回、排在多前面的指标                | Plan 10                              |
| Rerank                | 对初步候选再次排序的独立步骤                      | Plan 10 之后                           |
| Vector store          | 存储并近邻搜索向量的后端；如 SQLite-vec、Milvus    | Plan 8–12                            |

## RAG、搜索、微调与记忆的区别

| 概念       | 主要目标             | 知识存放位置                           | 文档更新后怎么办     | 是否天然有来源 |
|----------|------------------|----------------------------------|--------------|---------|
| 关键词/全文搜索 | 找字面匹配资料          | 搜索索引                             | 重建或增量更新索引    | 通常有     |
| RAG      | 找证据并据此生成答案       | 源文档 + 检索索引 + 本次上下文               | 更新源文档并重建相关索引 | 设计正确时有  |
| 微调       | 改变模型输出习惯、格式或特定能力 | 模型参数                             | 再训练或再微调      | 没有      |
| 对话记忆     | 保存用户偏好、会话状态或历史   | session / profile / memory store | 按会话或用户更新     | 不等于知识来源 |

RAG 可以使用向量检索，也可以融合关键词检索、结构化过滤和 rerank；“用了向量库”不等于完整实现了 RAG。同样，把聊天记录丢进向量库也不自动成为知识库
RAG。

## RAG 的特点与收益

- **可更新**：资料变更后更新索引，不必更新模型参数。
- **可引用**：答案可回到真实 URI、文件和 PDF 页码，便于人工核查。
- **可治理**：语料范围、租户、可见性和删除策略可以独立管理。
- **可评估**：可以先评估正确 chunk 是否被召回，再评估回答是否忠实于证据。
- **可替换**：parser、embedding、retriever、SQLite-vec、Milvus 和 ChatModel 都能在边界处替换。

这些收益有前提：源文档必须能正确提取，chunk 必须保留 metadata，filter 必须在检索层执行，生成器必须被约束为只使用证据。

## RAG 不能自动解决什么

- 检索不到、解析错误或无权限的资料，模型不会因此获得正确答案。
- 相似度高不等于事实正确；向量只提供候选排序信号。
- Prompt 约束降低幻觉，但不能替代引用校验和人工质量审查。
- 扫描 PDF、表格、多栏排版、图片和图表需要额外解析/OCR，不能假设提取文本天然可靠。
- RAG 不自动解决长期记忆、Agent 规划、工作流编排、缓存或生产可观测性。


Plan 2–12 逐步实现。
