# Plan 3：理解消息角色与对话记录

## 本节只解决什么

学会用 `system`、`user`、`assistant` 三种消息组织一次对话，并认识到“历史”就是按顺序保存的消息列表。

## 理论基础

LLM 并不天然知道哪段文本是规则、提问还是它此前的回答；聊天协议用角色赋予语义。

- `system`：应用给模型的稳定行为边界，例如回答语言、身份、禁止事项。
- `user`：当前用户的请求。
- `assistant`：此前模型的答复。下一轮把它带回去，模型才可能引用自己的前文。

最小输入通常是 `system + user`。多轮对话时，应用维护 `system + user + assistant + user + ...` 的顺序列表，再把完整列表交给模型。模型服务一般不会替你的进程永久保存这个列表；是否保存、保存多久、按哪个会话隔离，是应用自己的责任。

Plan 3 只验证消息的角色与顺序，因此不调用 LLM。`plan3_test.go` 中的切片就是一个最小“内存历史”，但它还没有长度控制、数据库持久化或用户隔离，这些是后续工程问题。

## 动手步骤

```bash
go test ./testfiles -run TestPlan3MessageRolesAndHistory -v
```

把测试中的用户问题换成自己的问题，观察消息顺序。尝试把 `assistant` 消息删掉，再思考第二轮模型少了什么上下文。

## 常见误区

- `system` 不是安全沙箱。用户输入和工具返回仍可能造成提示注入，生产系统需要额外边界。
- 历史越长不一定越好：会增加 token 成本，也会让模型忽略早期内容。入门阶段先正确保存，再考虑裁剪或摘要。
- 消息角色不是普通字符串约定；使用 `schema.SystemMessage`、`schema.UserMessage`、`schema.AssistantMessage` 可减少拼写错误。
